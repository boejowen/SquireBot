# Phase 42 — UI Design Contract

> Visual and interaction contract for the Wishlist polish phase (WISHUI-01 density compaction + WISHUI-02 sub-Velious tier badge). Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope of this contract:** web-only. WISHUI-01 tightens the spacing of the existing two-pane wishlist (`web/src/routes/wishlist/+page.svelte`); WISHUI-02 adds a small **tier badge** to each suggestion row and reorders the suggestion list as an upgrade ladder. The tier *data* (Kunark/classic rows, the `tier` field) is backend and out of this contract — this document governs only how the tier renders and how the compaction lands. **No new component, no restructure, no architecture change** (CONTEXT D-01, deferred-ideas §4). The watcher is untouched.

## Spacing Scale

Declared values (multiples of 4). The wishlist inherits the app 4/8/16/24/32 scale; WISHUI-01 shifts specific tokens **down one step** to match the Characters/Inventory density.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Row inner gaps, badge inline margin, chip gaps |
| sm | 8px | Compact element spacing, target/suggestion row inner gap, badge padding-x |
| md | 16px | Default element spacing, add-control gap (after compaction) |
| lg | 24px | Two-pane grid column gap (`.wishlist` — UNCHANGED, matches `/characters:313`) |
| xl | 32px | Shell-main page gutter (inherited, unchanged) |

### WISHUI-01 compaction map (exact before → after — CONTEXT D-01)

These are the ONLY spacing changes this phase. Each value is grounded in the current `wishlist/+page.svelte` CSS (line references are pre-edit). **The two-pane `.wishlist` grid gap (24px `lg`) is intentionally KEPT** — density polish tightens *within* the panes, not the master-detail column gap (which already matches `/characters:313`).

| Element | Selector (current line) | Before | After | Rationale |
|---------|-------------------------|--------|-------|-----------|
| Per-slot accordion gap | `.accordion` gap (`:1131`) | 24px | **16px** | Tighten inter-slot rhythm to the sibling-tab feel |
| Slot vertical padding | `.slot` padding (`:1137`, `16px 0`) | 16px | **12px** | Denser slot blocks; `.slot:first-child` still `padding-top: 0` |
| Target row min-height | `.target` (`:1242`) | 44px | **40px** | Still a valid touch target (≥40px); denser rows |
| Suggestion row min-height | `.sug` (shares `.target,.sug` block `:1236-1244`) | 44px | **40px** | Same; the two share the rule — one edit covers both |
| Add-control stack gap | `.add-control` gap (`:1348`) | 16px | **12px** | Tighten the add-open → field → results → suggestions stack |

**Touch-target floor:** 40px is the compaction floor for any tappable ROW (targets, suggestions). Standalone **buttons keep their 44px min-height** (`.add-open :1353`, `.slot-header :1150`, `.t-remove :1318`, `.add-pick :1404`, `.add-field input :1394`, `.sug-add`) — do NOT drop these to 40px; a control that is a single tap point stays at the 44px comfort target. The list-selection rows in the left pane (`.row :964`, `.item-result :1028`) also stay at 44px (they mirror `/characters` exactly).

**Exceptions:** the `.wishlist` grid gap stays at 24px (`lg`); `.detail` gap (`:1068`, 24px) and `.detail-header` gap (4px) are unchanged (they frame the pane, not the accordion density). No new spacing token is introduced.

## Typography

Type is **unchanged** this phase — the wishlist already uses the app type contract; the tier badge inherits the existing eyebrow/label idiom (the same treatment as the neighboring `.raid-tag`/`.sug-eyebrow`, which the badge sits beside). Declared for completeness so the checker can verify the badge conforms.

| Role | Size | Weight | Line Height | Where |
|------|------|--------|-------------|-------|
| Heading | 20px | `var(--weight-display)` (600; 400 minimalist) | 1.2 | `.detail-name`, `.no-targets-heading`, `.ex-name` |
| Body | 16px | 400 | 1.5 (rows 1.3–1.4) | `.sug-name`, `.t-name`, target/suggestion text, prices |

**Tier badge type (WISHUI-02):** the badge is a **Label/eyebrow** element — `font-family: var(--font-display)`, `font-weight: var(--weight-display)`, `font-size: 13px`, `text-transform: uppercase`, `letter-spacing: 0.04em`. This is byte-identical to the existing `.raid-tag` type (`:1286-1294`), so the four tier badges read as one family. **No new font size or weight** — the phase uses only the 3 roles above (well within the 3–4 size / 2-weight ceiling; `weight-display` is the single sanctioned per-theme weight variance already in the system).

## Color

The 60/30/10 split is the established site contract (unchanged this phase). Listed as the resolved velious-default hexes for reference; **implementation uses the `var(--…)` token, never the hex**, so all 5 themes stay consistent.

| Role | Token (velious hex) | Usage |
|------|---------------------|-------|
| Dominant (60%) | `var(--bg)` (#060b18) | Page background |
| Secondary (30%) | `var(--panel)` (#0f1729) | The two panes, rows, accordion surfaces |
| Accent (10%) | `var(--accent)` (#a8c5e0) | Eyebrows, selected-row rail, links, primary Add button, focus rings |
| Destructive | `var(--destructive)` → `var(--status-missing)` (#e88a8a) | The Remove-target control only |

**Accent reserved for:** slot/suggestion eyebrows, the selected list-row left rail (`.row.selected`), the `t-wiki`/quest links, the primary `.add-open` Add button fill, `.add-pick` hover, and all `:focus-visible` outlines. Accent is **not** applied to the tier badge (see below) and **not** used as a generic "interactive" color.

### Tier badge color mapping (WISHUI-02 — the load-bearing new color decision)

The badge is a **bordered, transparent-fill text pill** mirroring the `ExaminePanel` `.ex-flagchip` idiom (`ExaminePanel.svelte:148-160`) — `color` + `1px solid` border in the tier token, `border-radius: 3px`, `padding: 1px 6px`, no fill — so badge text sits on `--panel`, keeping it easy to clear the ≥3:1 non-text (border) contrast per theme. Per-tier token assignment (all four tokens exist in every theme):

| Tier label | Token | Why this token (theme-consistent, ≥3:1 border vs `--panel`) |
|------------|-------|--------------------------------------------------------------|
| `Classic` | `var(--status-other)` | The neutral/eyebrow tone (the same token the existing `.raid-tag` uses) — a calm "baseline tier" read |
| `Kunark` | `var(--status-other)` | Same neutral tone — group/pre-raid tiers share the eyebrow color; the **badge LABEL** distinguishes them, not the color (CONTEXT D-02: the UI just renders whatever tier text arrives) |
| `Pre-Raid` | `var(--status-other)` | Same — Velious Pre-Raid is a group tier |
| `Raid` | `var(--destructive)` (= `var(--status-missing)`) | The raiding tier reuses the existing destructive/not-for-sale tone — the SAME token the current `Raid`/`Not for sale` treatment already implies, keeping the "you can't buy this" signal (CONTEXT D-04) |

**Rationale for one shared token across the three group tiers:** CONTEXT D-02 is explicit — "the UI just renders whatever tiers arrive via the badge; no per-tier hardcoding beyond the badge label/color mapping." Coloring Classic/Kunark/Pre-Raid identically (neutral eyebrow) while the **text label** carries the distinction avoids inventing three new per-tier hues (there is no green/purple/blue "tier" token that exists across all 5 themes — velious/heavy/minimalist lack them, the same constraint that forced Phase 40 to add dedicated `--flag-*` tokens). The raid tier gets the one semantic escalation (`--destructive`) because it already has semantic meaning in the current code (`is_raid` → not-for-sale). **This is a two-color mapping over four labels — legibility comes from the label text, per D-02/D-03.**

**Contrast:** every candidate token (`--status-other`, `--status-missing`/`--destructive`) already clears ≥3:1 against `--panel` in all 5 themes (they are existing on-panel text/badge tokens — `--status-other` is the `.raid-tag`/`.ex-flags` color today, `--status-missing` is the `.t-remove` destructive text today, both live on `--panel` surfaces). Badge **text** sits at 13px on the transparent-fill pill, so it inherits the token's text contrast, which is already validated for these on-panel uses. No new contrast risk is introduced. Heavy's `--status-missing` (#6b1a1a, dark) as a **border + text on the dark `--panel` #1a0e05** is the one to eyeball at smoke time; if it reads too dim as a Raid badge in Heavy, fall back to the existing Heavy treatment of scoping the Raid badge text to `var(--accent)` (the same caveat `app.css:123-127` already documents for Heavy's destructive button) — planner's discretion, but do NOT introduce a literal hex.

**Existing Raid/not-for-sale treatment is KEPT (D-04):** the `Raid` tier badge is **additive** — it does not remove the existing `.raid-tag` "Raid" + `.not-for-sale` "Not for sale" spans (`:796-798`) or their price-suppression. The badge is the *ladder-position* label (Kunark-Raid vs Velious-Raid are both `[Raid]`); the existing not-for-sale spans remain the *purchasability* signal. If planner finds the badge `[Raid]` + the span `Raid` reads as duplicated, the span may be dropped in favor of the badge — but the `Not for sale` span and the price suppression MUST stay (that is the load-bearing "you can't buy this" contract).

## Interaction & State Contract

The wishlist's interactions are unchanged; this phase adds **one render element (the tier badge)** and **one ordering rule (the ladder)**. No new state, no new async, no new dialog.

### Suggestion-row ladder ordering (WISHUI-02 — D-03)

Within each equipment-slot accordion section, the per-slot `slot.suggestions` list renders as an **upgrade ladder, low → high**:

```
Classic  →  Kunark  →  Velious Pre-Raid  →  Velious Raiding
```

- The current alphabetic `ORDER BY wgt.tier` (`store/readviews.go:557`) is **replaced by an explicit tier RANK** low→high (Go tier-order map or SQL `CASE` — backend/planner's discretion, no new column since there is no migration).
- The Iksar minor tier sits at ~the Kunark level (CONTEXT "Claude's Discretion") — rank it adjacent to Kunark.
- The badge is what makes the ladder legible: a user scanning a slot sees `[Classic] … [Kunark] … [Pre-Raid] … [Raid]` top-to-bottom and reads the upgrade path.
- Ties within a tier keep the existing secondary sort (class, slot, rank) — the rank replaces only the leading `tier` sort key.

### Tier badge render (per suggestion row)

- Renders on **each** `.sug` row (`:789-823`), positioned with the existing row metadata (beside `.sug-name`, before/near the price/`.raid-tag` cluster). It is a static label — **no hover, no click, no focus target** (it is not interactive; it does not enter the tab order).
- The badge text is the tier label string surfaced from the new `WishlistSuggestion.tier` field (`compute/types.go` + `web/src/lib/api.ts`). The UI maps the raw tier string → a display label + a color token via a small pure lookup (the same shape as `$lib/flags`'s resolver). Unknown/absent tier → **omit the badge** (graceful degradation; never render an empty pill or a raw enum).
- Multi-suggestion legibility only — the badge does not change selection, examine, or add behavior (`examineSuggestion`/`doAdd` unchanged).

### States (all pre-existing — the badge/ladder must not regress them)

| State | Contract (unchanged this phase) |
|-------|--------------------------------|
| Loading | Existing `.corpus-loading` / skeleton behavior; tier badge simply absent until data lands |
| Empty (no targets) | `.no-targets` block (`:1102`) — heading + body copy unchanged; suggestions may still show below with badges |
| No suggestions for a slot | `.slot-empty` message unchanged; no badge rendered |
| Populated | Suggestion rows render the badge + ladder order; targets render as today |
| Reduced motion | Honored by the global `prefers-reduced-motion` rule (`app.css:155`); the badge has no animation anyway |

### Keyboard & a11y (must survive compaction)

- The 40px compacted rows **retain keyboard operability**: `.sug-name`/`.t-name` buttons keep their `:focus-visible` 2px accent outline (`:1261-1266`); the slot-header disclosure keeps its `:focus-visible` (`:1157`). Compaction changes only `min-height`/`gap`/`padding`, never removes a focus style or a tab stop.
- The tier badge is **decorative-adjacent text** — it is a `<span>` with visible text (not an icon), so it needs no `aria-label`; screen readers read the tier word inline. Do NOT add `aria-hidden` (the tier is meaningful information).
- Touch targets: interactive controls stay ≥44px (buttons) / the rows stay ≥40px — both clear the a11y comfort floor for this density tier (matches the ratified `/characters` + `/inventory` rows).

The wishlist's copy is established; this phase adds only the **four tier labels**. No new CTA, no new dialog, no new error surface.

| Element | Copy |
|---------|------|
| Primary CTA (unchanged) | "Add a target" (`.add-open`, `:780`) / "Add" (per-suggestion `.sug-add`, `:821`) |
| Tier badge — Classic | `Classic` |
| Tier badge — Kunark | `Kunark` |
| Tier badge — Velious Pre-Raid | `Pre-Raid` |

**Tier label mapping notes:** the *badge* labels are the short display forms above. Abbreviating avoids a badge wide enough to wrap the dense 40px row.
