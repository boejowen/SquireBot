<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → AddWantHandler | The POST body's `character_id` is untrusted; authorized server-side via `IsCharAssignedToTx` inside the tx before insert |
| client → ListGuildWantsHandler | Login-gated (RequireSession); returns all-members data minus the private note |
| bot goroutine → Discord | The embed is built server-side; the DM recipient is fixed to the want owner |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28-05 | Elevation/Tampering (IDOR) | AddWantHandler character_id | mitigate | `IsCharAssignedToTx` called in-tx BEFORE AddWantTx; `ErrCharNotAssigned`→403. Task 1 acceptance asserts the 403-on-unassigned path. |
| T-28-06 | Spoofing (wrong DM recipient) | wantmatch.Hit / ec send path | mitigate | `Hit.DiscordUserID` stays `wantlist_item.discord_user_id`; the embed change is display-only; a regression test asserts the target == want owner regardless of character_id (Task 2). |
| T-28-07 | Information Disclosure | ListGuildWantsHandler | mitigate | RequireSession (login-gated); the store read already excludes `note` (Plan 01). |
| T-28-08 | Tampering (embed/log injection) | "For" field, audit | mitigate | Embed field value is plain-text (not markdown/URL-interpolated); audit carries `character_id` as an id only (V7), never the name. |
| T-28-09 | Repudiation | wantlist_add audit | mitigate | `AppendAuditTx` records the tagged add with caller + item_id + character_id in the same tx. |
