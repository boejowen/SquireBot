# Phase 20 — UI Design Contract

> Visual and interaction contract for the three frontend surfaces of the notification spine (WANT-03, WANT-04, WANT-08). Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **This is NOT greenfield.** SquireBot ships a live SvelteKit site (squirebot.quest) with a fully established, approved design system (14-UI-SPEC), extended by the login-gated personal-CRUD forms (15-UI-SPEC § Form Contracts + ConfirmDialog), the `/account` list+revoke twin (17-UI-SPEC), and the `/wantlist` grid + per-row controls (19-UI-SPEC). **Every spacing / typography / color decision below is INHERITED from that system — nothing here invents a new palette, font scale, or component vocabulary.** This spec's job is to lock how three new/extended surfaces *reuse* what exists and to nail the phase-specific interaction contracts: the toggle vocabulary (prefs + officer kill-switches + per-want mute), the **delivery-status** encoding in the inbox (the load-bearing CAN'T-DM safety net), the **unread-count nav badge**, and the officer **"add channel" form + "send me a test alert"** pulse.
>
> **shadcn gate: N/A.** shadcn is React-centric; this is SvelteKit. The design system already exists (no `components.json`; tokens live in `web/src/app.css` + `web/src/lib/theme/themes.ts`). No initialization, no registry. This phase adds **no new frontend dependency** — it composes existing components + existing Lucide icons.
>
> **Phase scope (UI):** three surfaces, all behind existing gates. (1) a NEW login-gated `/notifications` page (Preferences + Inbox), reached by a NEW nav link with an unread-count badge; (2) a NEW "Monitors" section on the existing officer `/admin` page (RequireOfficer); (3) a NEW per-want mute bell on the EXISTING `/wantlist` grid. **NO Discord bot UI, NO DM rendering, NO monitor wiring lives in the frontend** — those are backend (the bot goroutine, `notify`, `wantmatch`). The frontend reads/writes prefs + the `alert_log` inbox + `guild_channel` rows + `wantlist_item.muted`, and fires the officer test-alert.

## Spacing Scale

Inherited unchanged from 14-UI-SPEC (8-point scale, multiples of 4). No new tokens; no phase-specific values.

| Token | Value | Usage (this phase) |
|-------|-------|--------------------|
| xs | 4px | Icon-to-label gap, badge inset, the delivery-badge pill inset, the unread-count badge inset, the mute-bell inset |
| sm | 8px | Toggle label↔switch gap, inbox row vertical padding, form label↔control gap, the CAN'T-DM hint line offset, result lines |
| md | 16px | Default element spacing, inbox row horizontal padding, gap between a pref toggle row and its description, add-channel field gaps |
| lg | 24px | `.form-card` padding, gap between Preferences and Inbox, gap between the Monitors sub-blocks (kill-switches / add-channel / test-alert), gap between `/admin` sections |
| xl | 32px | Page gutters (the shell `<main>` already supplies these) |
| 2xl | 48px | Empty-inbox (`no-notifications`) vertical centering block (reuses `StateBlock`'s `48px 16px`) |
| 3xl | 64px | Page-level whitespace on wide viewports (shell-owned) |

**Exceptions (inherited, unchanged):**
- **Touch targets:** every interactive control — each `Toggle` (master / per-monitor / kill-switch / mute bell), each mark-read button, "Mark all read", the add-channel fields + submit, the "Send me a test alert" button, the remove-channel button, and the nav `Notifications` link — gets a **44px minimum hit target** via padding (the documented a11y exception already used site-wide). The icon-only mute bell and per-row mark-read get the 44px target from padding around the ~16px glyph.
- **Unread badge:** the nav badge is a small inset pill (xs inset) sitting on the existing 44px nav link — the link, not the badge, carries the hit target.
- **Hairline borders:** 1px inbox-row / list separators and the divider rule are sub-token (borders, not spacing) and exempt.

## Color

Inherited single-palette table uses the **velious default** (all five themes catalogued in 14-UI-SPEC § Theme Catalog and shipped in `web/src/lib/theme/themes.ts`; values are the same CSS custom properties — no new colors). The 60/30/10 budget and the status-token semantics are unchanged.

| Role | Value (velious) | Usage (this phase) |
|------|-------|--------------------|
| Dominant (60%) | `#060b18` page bg / `#0f1729` `--panel` | App bg + the `.form-card` / inbox / list / dialog surfaces |
| Secondary (30%) | `#d4dee8` `--text` / `#4a6585`-class `--border` | Body text, the form-card border, row separators, the divider rule, the channel-list outlines, inactive toggle tracks |
| Accent (10%) | `#a8c5e0` `--accent` | **Reserved-for list below — never "all interactive elements".** |
| Destructive | `--destructive` (= per-theme `--status-missing`) | **Remove-a-channel only** — the resting remove button outline/text and the ConfirmDialog confirm fill. |

**Accent (`--accent`) reserved for, and ONLY for (inherited list, applied here):**
1. The **ON state of a `Toggle`** (the switch track/thumb fill when enabled) + its focus ring.
2. The active/focused state of the add-channel fields and any control (focus ring) + the **primary button fills**: the "Send me a test alert" button and the "Add channel" submit (accent fill / `--bg` text — the established `.primary` treatment).
3. The **selected/active nav entry** (`Notifications` when on that route) + the active sort caret if the inbox uses the grid.
4. The **unread-count nav badge** fill (accent fill, `--bg` text — see § Notifications Nav Badge) and the `bell-ring` glyph at small sizes.
5. Lucide icons at small sizes within the budget (bell, send, plus, mark-read check).
6. The "Mark all read" accent text action.

Body text, pref descriptions, inbox row text, the relative timestamps, inactive toggle tracks, and zebra striping do **not** use accent.

**Status / semantic colors (OUTSIDE the accent budget — they are data encoding, inherited from the `--status-*` triple):** the inbox **delivery status** is the load-bearing encoding and maps to the existing three tokens, ALWAYS with a WORD + icon (color is never the only signal):

| Delivery encoding | Token | Word + icon | Applies to |
|-------------------|-------|-------------|------------|
| **DELIVERED** — DM landed | `--status-ok` (have-it green) | word `DELIVERED` + `circle-check` | The status badge on a successfully-DMed alert row |
| **CAN'T DM** — Discord 50007 | `--status-missing` (rose-red) | word `CAN'T DM` + `triangle-alert` (or `mail-x`) | The status badge on a `dm_blocked` row — the safety-net row; ALSO carries the actionable hint line (see § Inbox CAN'T-DM Row) |
| **ERROR** — any other send failure | `--status-other` (neutral accent) | word `ERROR` + `circle-alert` | The status badge on a non-50007 failed attempt (transient/unexpected) |

> **Why CAN'T DM is rose-red, not neutral:** an undeliverable alert is the one delivery outcome the user must ACT on (enable server DMs) — it is a genuine fault state, so it earns the `--status-missing` red + the actionable hint, distinct from the neutral `ERROR` (a transient backend hiccup the user can't fix). This is the inverse of 19-UI-SPEC's custom-want chip (deliberately NEUTRAL because it's a valid choice, not a fault).

**Toggle color encoding (color is never the only signal):** the ON state is `--accent` track + the word **ON**; the OFF state is a muted `--border`/`--text@0.6` track + the word **OFF**. The per-want mute bell shows a filled `bell` (unmuted = alerts on) vs a struck `bell-off` (muted = alerts off) — the glyph swap carries the state, not just color.

**Contrast (inherited obligation):** verify body text vs surface and every badge word vs its tinted pill + the unread-badge count vs the accent fill meet WCAG AA (4.5:1) per theme; the velious defaults already clear AA, and the Heavy parchment caveat (dark ink on parchment, plus Heavy's ink-red `--status-missing` `#6b1a1a`) is handled by the existing `.eq-row` theme hooks — confirm the CAN'T-DM red word stays legible on Heavy.

## Notifications Nav Badge (D-05) — the load-bearing "you missed something" signal

The `Notifications` nav link (added to `SiteShell` inside `session?.authenticated`) carries an **unread-count badge**. This badge is load-bearing: it is how an UNDELIVERABLE (CAN'T-DM) alert actually gets noticed — without it, a 50007 alert silently rots in the inbox.

- **Resting (zero unread):** the bare `Notifications` link, no badge (a "0" badge is visual noise).
- **Unread (≥1):** a small accent-fill pill (accent bg, `--bg` text, Label 13px/600, tabular-nums, xs inset, ~9px radius) showing the count, abbreviated `9+` past 9 (or `99+` — pick one cap; default **`9+`** at this guild scale). The pill sits at the link's top-right.
- **Accessible name (mandatory):** the badge is NOT decorative. The link's accessible name MUST include the count, e.g. `aria-label="Notifications, 3 unread"` (and `aria-label="Notifications"` when zero). The visible count alone is insufficient for SR users.
- **Live update:** the count reflects `alert_log` rows with `read_at IS NULL` for the session owner. It updates after a mark-read / mark-all-read action (server-truth reload, mirroring the panel lifecycle) and on page load. Real-time push is OUT of scope (no websocket this phase) — a load/route-change refresh is sufficient.
- **Color-not-only:** the badge pairs the count with a `bell-ring` glyph on the link (or the count alone is acceptable since it is also exposed via the accessible name) — the accessible name is the non-color signal.

## `/notifications` Preferences Region (WANT-04 / D-01, D-02) — the user's own opt-out controls

The top region of the page. Renders the user's notify-prefs (a per-user prefs row in the Phase-20 migration: master + 3 per-monitor booleans). **All default ON (D-01)** — adding a want IS the opt-in; this region is the always-one-click-away mute.

**Layout:** a sub-heading ("Alert preferences") + a master toggle row, then the three per-monitor toggle rows, each as a `Toggle` + a Label-type name + a Body-type one-line description.

| Control | Default | Word/glyph | Description copy |
|---------|---------|------------|------------------|
| **Master — All alerts** | ON | `bell` (on) / `bell-off` (off) + ON/OFF | `Turn every SquireBot alert on or off. The per-monitor switches below only apply while this is on.` |
| EC-tunnel auctions | ON | ON/OFF | `DM me when a wanted item is auctioned in the EC tunnel.` |
| WTS cross-server | ON | ON/OFF | `DM me when a wanted item is posted for sale in a watched WTS channel.` |
| Raid targets | ON | ON/OFF | `DM me when a raid target tied to one of my quest wants is called.` |

**Interaction:**
- Toggling **Master OFF** visually de-emphasizes (dims, `aria-disabled` is NOT set — they stay readable, but the copy makes clear they're inert while master is off) the three per-monitor rows; their own stored state is preserved (turning master back ON restores them). The master-OFF state is the global mute (D-01).
- Each toggle writes server-side immediately (owner from session, D-02 — the page never sends an owner) with a polite `aria-live` confirmation ("Alerts turned off." / "EC-tunnel auctions turned on.") and server-truth reload; a failure surfaces the inline error copy and re-reads the authoritative state (never leaves the switch in a lying position).
- WTS/raid toggles being ON here does NOT mean those monitors are live — the officer kill-switch (D-08) is the other required gate. The descriptions say "when … in a watched channel" (honest: nothing fires until a monitor is enabled + a channel registered). No "coming soon" badge is required, but a muted note under the WTS/raid rows is acceptable Claude's-discretion polish: `These monitors switch on as the guild's officers enable them.` (default: **include this note** — it sets honest expectations).

## `/notifications` Inbox Region (WANT-04 / D-04, D-05) — the full alert history + 50007 safety net

The bottom region. Shows **every alert attempt** (D-04 — delivered, dm_blocked, error), newest-first, read/unread, reading `alert_log` (+ the new `read_at` read-state). It is BOTH "what was I pinged about?" and the can't-DM fallback.

**Sub-heading + bulk action:** a "Your alerts" sub-heading with a right-aligned **"Mark all read"** accent-text action (disabled when zero unread; 44px target; polite `aria-live` confirm on success).

**Each row (`NotificationRow` — list form, the default):** a single row, **md** horizontal / **sm** vertical padding, 1px `--border` bottom separator, that contains, left-to-right / top-to-bottom:
1. An **unread marker** — unread rows get a subtle leading accent dot + slightly stronger text weight is NOT allowed (only 2 weights); instead unread = a 2px accent left-border on the row + the row at full opacity, read = no left-border + `--text@0.8`. (Color-not-only: unread is ALSO conveyed by its inclusion in the badge count + by the per-row mark-read button being present/enabled.)
2. The **alert text** (Body): the item + source phrasing, e.g. `Fungi Tunic — seen at EC-tunnel auction` / `Rubicite Boots — posted WTS in <server>` / `Raid target for your quest want: <NPC>`. Item/source/NPC are user/wiki-controlled → render ONLY via plain `{}` (auto-escaped), NEVER `{@html}`.
3. The **delivery-status badge** (the § Color delivery encoding): `DELIVERED` / `CAN'T DM` / `ERROR` — word + icon + `--status-*` tinted pill.
4. A **relative timestamp** (Body, muted, tabular-nums) — e.g. `2h ago` / `yesterday` (a `title`/`datetime` carries the absolute time).
5. A per-row **mark-read** control (icon-only `circle-check` button, 44px target, `aria-label="Mark read"`), present only on unread rows; clicking marks just that row read (server-truth reload).

> **Grid alternative:** if a `DataGrid` instantiation is chosen instead of the list, the columns are `When` (timestamp, default-sort desc) · `Alert` (text) · `Source` (facet filter: EC / WTS / Raid / Test) · `Status` (facet filter: DELIVERED / CAN'T DM / ERROR) · `Read` (the mark-read control). Default sort newest-first. The unread visual still uses the 2px accent left-border treatment. Choose the grid ONLY if facet-filtering by status is wanted; otherwise the simpler list reads cleaner for a personal log. **Default recommendation: the list** (lower ceremony, matches the "my alerts" home framing).

### Inbox CAN'T-DM Row (D-05 / Pitfall 3) — the actionable safety net

A `dm_blocked` (50007) row is visually distinct and ACTIONABLE — not just a red dot:
- Status badge: `CAN'T DM` in `--status-missing` + `triangle-alert`.
- A **hint line** directly under the alert text (Body, `--status-missing` at reduced emphasis or `--text` with the warning glyph carrying the color): **`We couldn't DM you — Discord is blocking messages from the server. Turn on "Allow direct messages from server members" in your Discord privacy settings to receive these.`** (This is the load-bearing copy — see § Copywriting.)
- The hint is informational text, not a link (we can't deep-link Discord settings reliably). A "Retry delivery" action is explicitly **deferred** (CONTEXT § Deferred) — do NOT add it this phase.
- These rows still participate in the unread count + mark-read (the user can acknowledge them).

**Empty state:** when the owner has zero alert rows, render `StateBlock kind="no-notifications"` (new kind) — heading **"No alerts yet"**, body `You'll see your SquireBot alerts here once a monitor matches one of your wants. Make sure your wantlist has the items you're after.` The Preferences region stays visible above it.

## `/admin` Monitors Section (WANT-08 / D-06, D-07, D-08, D-10) — officer controls

A NEW third `.form-card` `<section class="form-card">` titled **"Monitors"** appended to the existing `.admin-area` on `/admin` (RequireOfficer — the existing two-layer authorization: Layer-1 UX `officers-only` `StateBlock` for direct-nav non-officers, Layer-2 the server re-check; identical to Evict guildie / Manage officers). Three sub-blocks, lg-gapped:

**1. Per-monitor kill-switches (D-07/D-08 — guild-wide on/off):** three `Toggle` rows (EC-tunnel auctions / WTS cross-server / raid targets), each with a Label name + a Body description. **EC defaults ON; WTS + raid default OFF/dark** (invite-gated — they ship dark, flip on as invites arrive, NO redeploy). The OFF (dark) state is the muted track + word **OFF**; a muted note on the dark monitors: `Ships dark — enable once the bot is invited to the source channels.` These are GUILD-WIDE (distinct from the user's own per-monitor opt-in): an alert fires only when BOTH the officer flag is ON AND the user opted in.

**2. Add channel form (D-07 — writes `guild_channel` rows):** a `FormField` form (reusing the `BankCoinForm`/`EvictionForm` shape) with:

| Field | Control | Required | Notes |
|-------|---------|----------|-------|
| Server label | text input | yes | A human label for the source server (e.g. `Raid Alliance — Red`). Renders back via plain `{}`. |
| Channel ID | text input (`inputmode="numeric"`, `pattern="[0-9]*"`) | yes | The Discord channel snowflake. Client-validates non-empty + numeric (UX defense-in-depth; the server re-validates). |
| Monitor type | native `<select>` | yes | Options: `EC-tunnel auctions` / `WTS cross-server` / `Raid targets` — maps to the monitor the channel feeds. |

Primary CTA: the established `.primary` accent button — label **"Add channel"** (`plus` glyph) — disabled until all three are valid; a `LoaderCircle` spin + "Adding…" during the request; polite `aria-live` success.

**3. Registered channels list:** below the form, a list of the registered `guild_channel` rows — each row: the server label + a muted `#<channel-id>` + a monitor-type Label chip + a per-row destructive **Remove** button (the shipped `.revoke-btn` treatment: `--destructive` text + 1px `--destructive` outline, transparent fill, `trash-2` glyph + "Remove", 44px). Remove is **confirm-before-commit** via the shared `ConfirmDialog` (this is the ONE destructive action this phase). Empty list → a quiet inline note `No channels registered yet. EC-tunnel monitoring uses PigParse and needs no channel; WTS and raid monitors need a channel here.` (the EC monitor is PigParse-polled, not channel-read — the note prevents officer confusion). All officer mutations are IDOR-safe + **audited** (the `audit.go` seam).

**4. "Send me a test alert" button (D-10 — the bot pulse):** a `.primary` accent button (`send` glyph) labeled **"Send me a test alert"** that DMs a sample alert to the CLICKING officer and logs it to THEIR inbox. It is the end-to-end proof (gateway-up + DM-send + inbox-log) and naturally exercises the 50007 path if the officer's own DMs are off. Feedback:
- **Success (DM delivered):** polite `aria-live` success line in `--status-ok`: `Test alert sent — check your Discord DMs (and your Notifications inbox).`
- **Blocked (50007):** a `--status-missing` line: `We couldn't DM you — Discord is blocking messages from the server. It's logged in your Notifications inbox; turn on server DMs in Discord to receive alerts.` (mirrors the inbox hint — same safety-net copy).
- **Bot down / error:** a `--status-other`/`--status-missing` line: `Couldn't send the test alert — the bot may be offline. Nothing was sent; try again shortly.`

## Per-Want Mute on `/wantlist` (WANT-03-adjacent / D-09) — the `WantMuteCell`

A NEW per-row control on the EXISTING `/wantlist` grid: a **bell / bell-off toggle** ("stop pinging me about THIS item"). Backed by `wantlist_item.muted` (new boolean in the Phase-20 migration).

- **Placement:** a new column in `wantlistColumns` (`columns.ts`), mounted via the same `renderComponent` FlexRender path as `WantRemoveCell`. Default position: a trailing **"Alerts"** column just before Remove (or a compact leading bell — default **trailing "Alerts" column** so it reads as a per-row setting, not a primary action). No sort, no filter.
- **States (glyph carries meaning — color-not-only):**
  - **Unmuted (default):** a filled `bell` glyph, `--text` (not accent — it's the resting/normal state), `aria-label="Alerts on for <item> — click to mute"`.
  - **Muted:** a struck `bell-off` glyph, `--status-other` muted, `aria-label="Alerts muted for <item> — click to unmute"`. A muted row's bell is the ONLY visual change (do NOT dim the whole row — the want is still active, just quiet).
- **Interaction:** click toggles `muted` server-side (owner from session — the call sends the want's id only, never an owner; IDOR-safe + audited), then server-truth reload (mirror the existing add/remove lifecycle — NEVER optimistic-mutate). 44px target. Polite `aria-live`: `Muted alerts for <item>.` / `Unmuted alerts for <item>.`
- **Custom wants:** a custom want (`item_id` NULL) already "won't trigger alerts" (19-UI-SPEC custom chip). The mute bell on a custom row is **disabled/absent** (muting an un-matchable want is meaningless) — render a muted `—` or omit the control, with `aria-label`/title `Custom wants never trigger alerts.` (default: **render a disabled bell-off `—`** so the column stays aligned).

## Toggle Vocabulary (the one new primitive)

A single small `Toggle` component backs every on/off control this phase (user prefs ×4, officer kill-switches ×3) — the per-want mute uses the bell-glyph variant (§ above) rather than the track switch, but shares the a11y contract.

- **Markup:** a `<button role="switch" aria-checked={on}>` (NOT a checkbox styled as a switch — the button is simplest with Svelte 5 runes) with a visible **ON / OFF** word (Label 13px/600) beside the track, so state is never color-only.
- **Visual:** OFF = muted `--border` track + `--text@0.6` thumb + word OFF; ON = `--accent` track + `--bg` thumb + word ON. 44px hit target. Focus ring `--accent`. Honors `prefers-reduced-motion` (the thumb slide goes instant).
- **Label association:** each toggle has an adjacent Label-type name; the `role="switch"` button's accessible name is the monitor/pref name (`aria-label` or `aria-labelledby` the name element).
- **Reuse:** this same `Toggle` is reused by future phases (it's deliberately generic). It is the only net-new visual primitive; everything else composes shipped components.

## Accessibility & Interaction Notes (inherited obligations)

- **Color is never the only signal (load-bearing this phase):** every delivery status (DELIVERED / CAN'T DM / ERROR) carries its WORD + an icon, not just a hue; every `Toggle` carries the ON/OFF word; the mute bell carries the bell vs bell-off glyph swap; the unread nav badge carries its count in the accessible name. A monochrome / color-blind user can read every state.
- **Keyboard:** every `Toggle` is a `role="switch"` button — Space/Enter toggles; mark-read, mark-all-read, add-channel fields + submit, test-alert, remove-channel, and the nav link are all Tab-reachable; `ConfirmDialog` traps focus and restores it. Visible focus ring in `--accent`.
- **Touch:** 44px min targets on every control (toggles, mark-read, mute bell, buttons, nav link).
- **Screen readers:** the unread badge MUST be in the link's accessible name (`aria-label="Notifications, N unread"`); each toggle's accessible name is its pref/monitor name; status changes + sends announce via polite `aria-live`; the inbox unread/read distinction is conveyed beyond color (badge count + mark-read presence).
- **Reduced motion:** honor `prefers-reduced-motion` (the global `app.css` rule); the toggle thumb slide, any test-alert spinner, and the dialog fade go instant.
- **XSS trust boundary (inherited, load-bearing):** alert text, item names, source/server labels, NPC names, and the officer-entered server label are user/wiki/officer-controlled. They render ONLY via plain `{}` (Svelte auto-escapes) — NEVER the raw-HTML directive. The single sanctioned `{@html}` sink in the app remains `ItemTooltip` → `composeItemNote` (not used on these surfaces). A channel label and an alert line must be inert text.
- **Server-truth / IDOR (inherited, D-02):** the prefs owner, the inbox owner, and the mute owner are derived SERVER-side from the Discord session — the page never sends an owner; the mute/mark-read/pref calls send only the relevant id. Officer routes are RequireOfficer + audited. A 401/403 bubbles to AuthGate → LoginScreen (prefs/inbox/mute) or collapses the admin UI to the `officers-only` refusal (monitors) via the existing `authGuard`.
- **noindex (inherited):** the site is `noindex`; these login-gated surfaces inherit it.
