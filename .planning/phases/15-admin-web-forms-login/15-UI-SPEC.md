# Phase 15 — UI Design Contract

> Visual and interaction contract for the Discord-OAuth login gate + the three authenticated web forms (eviction / bank-coin / admin-mgmt) added to the live P14 SvelteKit site. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **This phase EXTENDS the shipped P14 design system — it does NOT reinvent it.** P14 is live at https://squirebot.quest with a complete, checker-approved contract (`.planning/phases/14-web-frontend/14-UI-SPEC.md`) and an implemented token system in `web/src/app.css`. Every new surface MUST reuse the existing CSS custom properties (`--bg --panel --text --accent --status-ok --status-missing --status-other --font-display --font-body --weight-display --row-bg --row-text`), the 5-theme `[data-theme]` registry (velious default, WEB-05 carries forward), the `SiteShell`, `StateBlock`, `DataGrid`, `StatusCell`, `ItemTooltip`, and `ThemePicker` components, and the existing control styling (the `SearchBox` field, the `.tab` view-nav, the native `<select>` ThemePicker). All tokens below restate the P14 contract verbatim for the executor's convenience — they are NOT new values.
>
> **Decisions are LOCKED (15-CONTEXT D-01..D-12).** This contract derives entirely from those decisions + the existing `web/` system + the v1 sidebar behavioral oracles (`apps-script/src/triggers/showEvictionSidebar.ts`, `showAdminMgmtSidebar.ts`). No new design questions were opened.
>
> **Phase scope shift vs. P14:** P14 was **read-only, public, no login.** P15 turns the site into a **members-only, write-capable app** — a whole-site Discord login gate (D-01), a signed-in identity in the shell (D-03), and three write forms, two of which are **officer-only** (eviction, admin-mgmt) and one **any-authenticated-member** (bank-coin, D-12). P15 therefore introduces this project's **first destructive actions** (eviction, admin-removal) and its **first `--destructive` token usage** — both previously unset/N-A in P14.

| Secondary (30%) | `#1a2438`→`#0f1729` (header gradient) / `#d4dee8` (`--text`) / `#4a6585` (`--border`, dividers, field borders) | Structural chrome: form-card borders, field borders, list-row separators, dialog border, secondary text, the Admin-area panel chrome. |
| Accent (10%) | `#a8c5e0` (`--accent`, icy blue) | **Reserved-for list below — never "all interactive controls".** |

Reserved for the eviction + admin-remove confirm buttons and the destructive-consequence callouts only. |

**Accent (`--accent`) reserved for, and ONLY for (extends the P14 list):**
1. The **primary action buttons** ("Sign in with Discord", "Save coin", "Add officer", and the eviction *preview*/confirm primary) — accent fill with `--bg` text, mirroring the existing `.retry` button.
2. **Focus rings** on every form control, button, and the dialog (`outline: 2px solid var(--accent)`), matching `SearchBox`/`ThemePicker`/`.tab`/`.retry` focus styling already shipped.
3. The **active "Admin" nav tab / current-section indicator** in the shell (same treatment as the existing `.tab.active`).
4. The **signed-in username link / sign-out affordance** hover/focus accent, and the **officer `shield` badge** glyph.
5. Lucide glyphs at small sizes (login, sign-out, coins, shield, confirm icons).

Body text, help copy, inactive controls, input field backgrounds (`--panel`), list-row backgrounds, the owner-floor "(owner)" annotation, and disabled buttons do **NOT** use accent. **The destructive red (`--status-missing`) is the ONLY non-accent chrome color** and is confined to the destructive confirm buttons + their consequence callouts.

**Status / data-encoding colors (unchanged from P14):** `--status-ok` / `--status-missing` / `--status-other` continue to encode gear/spell status in the (unchanged) grids. The eviction *preview* may reuse `--status-missing` as a subtle tint on the "will be removed" character list (data-encoding + destructive framing aligned). The bank-coin form does not introduce new status colors.

**Contrast:** all five themes already clear WCAG AA for body-on-surface in P14. New surfaces (form cards, login card, dialog) use the same `--text`-on-`--panel` pairing, so they inherit AA. The destructive button uses `--bg` text on a `--status-missing` fill — the executor MUST verify AA for that pairing per theme (velious `#060b18` on `#e88a8a` clears; Heavy's `#6b1a1a` is dark, so on Heavy the destructive button uses `--accent`-colored **text on a dark `--status-missing`-tinted** treatment rather than dark-on-dark — budget QA on Heavy's destructive button exactly as P14 budgeted QA on Heavy's inverting grid).

## Information Architecture & Authorization (the navigation contract)

How the new surfaces fit the shipped shell, and how officer-only surfaces are hidden — this is the load-bearing IA the CONTEXT requires the spec to define.

**Whole-site gate (D-01):** `AuthGate` wraps `SiteShell` at the layout level. Resolution order on load:
1. **Auth-loading** — brief `StateBlock kind="auth-loading"` while the session is resolved against the backend (`GET` a session/whoami-style endpoint that returns `{ authenticated, isMember, isOfficer, username, avatar, discord_user_id }`; exact endpoint is a backend-plan detail).
2. **Unauthenticated** → `LoginScreen` (no shell nav, no views).
3. **Authenticated but not a guild member** → `NotMemberScreen` (AUTH-08 refusal; no views).
4. **Authenticated guild member** → the full app (shell + views + the forms they're allowed to reach).

**Navigation map (post-auth):**

| Surface | Route (suggested) | Visible to | Reached via |
|---------|-------------------|-----------|-------------|
| The 4 views (`view`/`gear_check`/`spell_check`/`bank`) | `/` (unchanged) | any authenticated member | existing view-nav tabs |
| **Record bank coin** (`BankCoinForm`) | `/bank-coin` | **any authenticated member** (D-12) | a control **on/near the `bank` view** (e.g. a "Record coin" button in the bank panel toolbar) **and** a shell nav entry — reachable without being an officer |
| **Admin area** (`EvictionForm` + `AdminMgmtForm`) | `/admin` (with two sub-sections / tabs: "Evict guildie", "Manage officers") | **officers only** (D-06/D-09) | an **"Admin" nav entry in `SiteShell` that renders ONLY when `session.isOfficer`** |

**Hiding officer-only surfaces — the two-layer contract (ports v1's exact pattern):**
- **Layer 1 (UX):** the "Admin" nav entry and any deep links to `/admin` are **not rendered** when `session.isOfficer` is false. A non-officer never sees the affordance. (Mirrors v1's "Remove button suppressed on floor row when caller != floor" client-side suppression.)
- **Layer 2 (security boundary):** **the server is the authority.** Every officer-only read AND write endpoint re-checks the session's officer status server-side and **authorizes inside the write transaction** (D-06 — closes v1's WR-04 TOCTOU window: a just-removed officer must not get one final write through). The frontend MUST handle a `403`/`not_authorized` response from any officer endpoint by routing to a clear "you are no longer an officer" message and collapsing the Admin UI — never assume the hidden nav is sufficient. **Frontend gating is UX only; the read API + form endpoints are the gate (D-01).**
- A non-officer who navigates directly to `/admin` (typed URL) sees a **"Officers only" refusal block** (`StateBlock`), not a broken page and not the form.

**LoginScreen / NotMemberScreen do NOT carry the view-nav or the forms** — they are pre-auth and render inside a minimal themed shell (wordmark + the centered card only; the `ThemePicker` MAY appear so the EQ identity shows pre-login, but no view nav, no Admin entry, no session indicator).

## Login & Auth Surfaces (AUTH-08 / AUTH-09)

### LoginScreen
- **Layout:** vertically + horizontally centered card (max-width ~420px) on the themed `--bg`; card surface `--panel`, `--border`, `lg` (24px) padding, subtle shadow (matches form cards).
- **Contents, in order:** the **wordmark** (Display 28px, `--accent`, `--font-display`) → a **one-line purpose** (Body 16px): the exact copy in the Copywriting Contract → the **"Sign in with Discord" primary button** (accent fill, `--bg` text, `log-in`/Discord glyph, 44px min height, full card width) → a small footnote line stating membership is required.
- **Interaction:** the button triggers the **server-side OAuth start** (D-04 — navigates to the backend's `/auth/login` style route; the client secret never touches the frontend). No client-side Discord SDK. While the redirect is in flight, the button shows an in-flight state (`loader-circle`, label "Redirecting…", disabled).
- **Reduced motion:** any card entrance is instant under `prefers-reduced-motion` (global rule already in `app.css`).

### NotMemberScreen (the AUTH-08 refusal)
- Reached when Discord auth succeeds but the configured guild ID is **absent** from the user's `guilds` list (D-02 — membership = guild present in the list, no bot).
- **Layout:** same centered card; heading (20px) + body (16px) per the Copywriting Contract, a `shield-alert` glyph in `--status-missing`, and **two actions**: a primary **"Sign in as someone else"** (restarts OAuth) and a secondary text link to the guild's Discord invite is **out of scope** (no invite is configured) — instead the body tells them to join the guild Discord and try again.
- **No data, no nav** — this user has no authorized surface.

### SessionIndicator (in `SiteShell`, post-auth)
- Right side of the shell header, after the `ThemePicker`: the Discord **avatar** (small rounded image from the Discord CDN; fall back to a `user` glyph in a `--panel` circle if no avatar) + the **username** (Label 13px). If the session is an officer, a small `shield` badge in `--accent` precedes the username.
- Click opens a minimal menu (or the username itself is a button) exposing **Sign out** (`log-out` glyph). Sign-out hits the backend's session-destroy route and returns to `LoginScreen`.
- 44px min touch target; accent focus ring; the menu dismisses on Esc / outside-click / selection.

## Form Contracts

All three forms share the **same field rhythm and control styling** (continuous with the shipped `SearchBox` field + `ThemePicker` select): label (Label 13px/600 display, uppercase, `--accent`-free unless it is the active focus) above its control; control = `--panel` background, `1px var(--border)`, 4–6px radius, `16px`/`--font-body` text, **44px min height**, `outline: 2px solid var(--accent)` on focus. Inline help/error text below the control at Body 16px (error in `--status-missing`). Each form lives in a `--panel` card with `lg` (24px) padding under a Heading-20px title. Each form's action row is right-aligned (or full-width on narrow screens) with the primary button in `--accent`.

### 1. BankCoinForm (ADMIN-05 — any authenticated member, D-12)
**Flow:** select an `is_bank_toon` character → enter platinum / gold / silver / copper → **Save coin** → success confirmation; the value then surfaces in the `bank` view (D-11, replacing the "not yet recorded" affordance).

- **Character select:** a native `<select>` of `is_bank_toon` characters (matches the `ThemePicker`/v1 eviction `<select>` pattern). If the chosen character already has coin recorded, **pre-fill the four inputs** with the current values so the form edits rather than blindly overwrites.
- **Four number inputs** (`type="number"`, `inputmode="numeric"`), labeled **Platinum / Gold / Silver / Copper**, arranged in a single row on wide screens, stacked on narrow. `tabular-nums`.
- **Validation (locks CONTEXT D-11 discretion item):** platinum is a free non-negative integer (`min=0`, no upper bound — a guild bank can hold large plat); **gold / silver / copper are bounded `0–999`** (the EQ coin system carries at 1000 → next denomination; this is the recommended bound, lock it). Reject negatives and non-integers inline with the field-level error copy below; the **Save coin** button is disabled until inputs are valid and at least one differs from the loaded value.
- **Empty / states:** if there are **no `is_bank_toon` characters**, show `StateBlock kind="no-bank-toons"` (copy below) instead of the form. Save in-flight → button shows `loader-circle` + "Saving…", disabled; success → `form-success` confirmation (copy below) + the select stays so a second entry is easy; failure → `form-error` inline ("…No changes were saved.").
- **No confirm dialog** — bank-coin is non-destructive and member-accessible; a plain save with a success toast is correct. NOT officer-gated (D-12).

### 2. EvictionForm (ADMIN-04 — officer-only, D-09/D-10) — ports `showEvictionSidebar.ts`
**Flow:** pick a guildie (owner) → **preview** their character cascade + the 30-day grace date + the guild-code-revoke consequence → **explicit confirm** → result. **Confirm-before-commit is mandatory** (the v1 UX, now a themed dialog instead of `window.confirm`).

- **Guildie select:** a native `<select>` of evictable owners (distinct owner identities with at least one non-removed character; v1 `getEvictionEmails` semantics — but keyed/labeled by the guildie's identity as the DB now models it; the planner picks owner-email vs Discord-linked label). Placeholder "Choose…". Until a guildie is chosen, the preview and the Evict button are hidden/disabled (v1 behavior).
- **Preview block** (appears on selection, mirrors v1's `previewEviction`): a heading "Characters affected (N):" + the **list of every character** that will be flagged `is_removed`, rendered with a subtle `--status-missing` tint (destructive framing); then a grace line "Grace expires: <date> (30 days from today)."; then a **consequence callout** (D-10): a `triangle-alert` + the copy stating eviction **also immediately revokes their guild code** so their watcher stops uploading, and that it's **reversible during the grace period**. Empty cascade → "No characters found for this guildie." + Evict disabled.
- **Owner-floor protection (D-09):** if the selected guildie is the owner-floor's own guildie data and the acting officer is a **peer** (not the floor), the Evict action is blocked — surface the protection inline ("Owner-floor protected — a peer officer can't evict the maintainer's data.") and disable Evict. (Server is the boundary; this is UX.)
- **Confirm:** the **Evict guildie** primary button (in the preview block) opens `ConfirmDialog` (destructive variant) restating the count + the guild-code-revoke + the reversibility, with a **destructive-colored confirm** ("Evict <guildie>") and a Cancel. v1 used `window.confirm`; P15 uses the themed dialog. Only on dialog-confirm does the commit fire.
- **Result:** success → `form-success` ("Marked N character(s) as removed; their guild code is revoked; grace until <date>."); failure → `form-error` ("Eviction failed: <reason>. No changes were written.") with the Evict button re-enabled. (v1 message shapes are the oracle.)

### 3. AdminMgmtForm (ADMIN-06 — officer-only, D-06/D-07/D-08) — ports `showAdminMgmtSidebar.ts`
**Flow:** list current officers → promote by **picking a logged-in user** (D-07) → remove per row (with owner-floor protection + confirm).

- **Current officers list:** a list (matches v1's `<ul>`), each row = the officer's identity (Discord username + avatar, since identities are now captured per D-03) + an annotation. The **owner-floor** row is annotated **"(owner)"** and shows a tooltip explaining the lockout (v1 copy). A **Remove** button per row, **EXCEPT** the owner-floor row when the caller is a peer (suppress the button — v1's `showRemove` rule). Heading shows the count: "Current officers (N):".
- **Promote (D-07 — pick, don't type):** instead of v1's free-text email input, render a **picker of users who have already logged in** but are not yet officers (the captured Discord identities from D-03) — a `<select>` (or a searchable list if the roster is large) of username + avatar. Selecting + **Add officer** promotes them. **No snowflakes typed, no typos** (the D-07 win). If **no promotable users** exist (everyone who's logged in is already an officer, or no one else has logged in yet), show `StateBlock kind="no-promotable-users"` with the copy below (it explains the "must sign in once before promotion" trade-off).
- **Owner-floor / self-removal (D-08):** a peer cannot remove the floor (button suppressed + server rejects with `owner_floor_protected`). Self-removal follows v1's documented orphan-pointer rule (allowed for non-floor; the floor cannot remove itself away to nothing). Route the `owner_floor_protected` / `not_authorized` / `lock_busy` errors to the exact inline messages v1 uses (see Copywriting).
- **Remove confirm:** the **Remove** button opens `ConfirmDialog` (destructive variant): "Remove <username> as an officer? They'll no longer be able to evict guildies or manage officers. Reversible — you can re-add them here." destructive confirm + Cancel. (v1 used `window.confirm`; P15 uses the dialog.)
- **Add result / Remove result:** success → `form-success` ("Officer added: <username>." / "Officer removed: <username>."); idempotent no-ops surface gently ("Already an officer: <username>." / "Not in the list: <username>."). Audit is server-side (append-only `audit_log`, D-06) — no UI surface required this phase.

### ConfirmDialog (shared destructive-confirm modal)
- **Why it exists:** P15 has two destructive actions; v1 used the browser's `window.confirm`, which can't carry the EQ theme or the consequence detail. P15 replaces it with a themed, focus-trapped modal — this is the single destructive-confirmation pattern for the phase.
- **Visuals:** centered modal over a dimmed backdrop (`color-mix` of `--bg` at ~70%); modal surface `--panel`, `--border`, `lg` padding, max-width ~440px. Heading (20px) + a `triangle-alert` in `--status-missing` + the consequence body (16px) + an action row: **destructive confirm button** (`--status-missing` fill / `--bg` text — see Heavy caveat in § Color) labeled with the specific action ("Evict <guildie>" / "Remove <username>") and a neutral **Cancel** (text/ghost button, `--text`).
- **Interaction:** focus moves to the dialog on open (focus the Cancel by default — destructive action is never the default focus); **Esc, backdrop-click, and Cancel all dismiss** with no side effect; only the explicit destructive button commits. `role="dialog"` + `aria-modal="true"` + labelled by the heading. Reduced-motion → instant.

| Element | Copy |
|---------|------|
| **Primary CTAs** | Login: **Sign in with Discord** · Bank-coin: **Save coin** · Eviction: **Evict guildie** (and dialog confirm **Evict <guildie>**) · Admin promote: **Add officer** · Admin remove: **Remove** (dialog confirm **Remove <username>**) |
| LoginScreen purpose line | `Sign in with Discord to see the guild's inventory, gear, and bank.` |
| LoginScreen footnote | `You must be a member of the guild's Discord server.` |

## Accessibility & Interaction Notes

- **Keyboard:** all form controls, buttons, the login/sign-out, the promote picker, and the dialog are Tab-reachable in source order; `ConfirmDialog` traps focus and restores it to the trigger on close; Enter submits a focused form's primary action where natural (e.g. the admin add-input, mirroring v1's Enter-to-add); Esc dismisses the dialog and the session menu. Visible focus ring in `--accent` everywhere (matches shipped controls).
- **Touch:** 44px min targets on every interactive element (see Spacing exceptions); the session menu and dialog dismiss on outside-tap.
- **Screen readers:** form fields use real `<label for>`; inline errors are `aria-live="polite"` (matches v1's `#msg aria-live`); the dialog is `role="dialog" aria-modal="true"` labelled by its heading; the officer `shield` badge has an accessible label ("Officer"); avatar images have `alt` = the username.
- **Color is never the only signal:** the destructive red is always paired with explicit copy ("Evict", "Remove", consequence text) and an icon; the owner-floor protection is conveyed by text + a disabled/absent button, not color alone.
- **Reduced motion:** the global `prefers-reduced-motion` rule in `app.css` already makes transitions instant; dialog and menu open/close, and the login in-flight spinner, MUST honor it.
- **Auth state is server-truth:** the frontend MUST treat a `401` (no/invalid session) by routing to `LoginScreen` and a `403` (not officer / not member) by routing to the matching refusal — never render stale authorized UI after the server says no (D-01 gate is at the API).
