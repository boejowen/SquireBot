Backend auth endpoints (15-02, on https://api.squirebot.quest — the API origin, NOT the apex site origin):
- GET  /api/v1/auth/login        → 302 to Discord (start the flow; the browser navigates here directly, NOT fetch).
- GET  /api/v1/auth/callback     → backend handles, redirects to the site (`/` or `/?not_member=1`).
- GET  /api/v1/auth/whoami-web   → 200 {authenticated:bool, isMember?:bool, isOfficer?:bool, username?:string, avatar?:string|null, discord_user_id?:string}. authenticated:false for no/expired session.
- POST /api/v1/auth/logout       → 204 (then navigate to `/`).
- The read endpoints (/api/v1/meta, /api/v1/views/*) now require the session cookie (401 without it).
- CORS allows the exact site origin + Access-Control-Allow-Credentials:true — so the browser sends the cookie ONLY when the request uses credentials:'include'.

P14 frontend conventions (web/src/) to mirror:
- api.ts (web/src/lib/api.ts) — API_BASE from `env.PUBLIC_API_BASE` ($env/dynamic/public, default https://api.squirebot.quest); getJSON<T>(path, fetchFn=fetch) throws a branded ApiError on non-2xx/transport/malformed-JSON. THIS PLAN edits getJSON's fetch options to add `credentials: 'include'` so every read carries the cookie, and adds an `ApiError.status === 401` signal the page can act on.
- Components are Svelte 5 runes ($props/$state/$derived/$effect); the project forces runes (svelte.config.js). +layout.svelte owns the [data-theme] + wraps children in SiteShell (bind:theme). +page.svelte fetches all 5 endpoints onMount and renders loading/error/ready via StateBlock.
- StateBlock.svelte (web/src/lib/components/) has kinds empty|view-empty|error|loading|no-results|no-coin — EXTEND with auth-loading + an officers-only refusal kind (or reuse error/empty with copy). Copy from UI-SPEC Copywriting Contract verbatim.
- Tokens (web/src/app.css): per-theme [data-theme] blocks define --bg --panel --text --accent --status-ok --status-missing --status-other --font-display --font-body --weight-display (+ --row-bg/--row-text for heavy). P14 left --destructive UNSET — THIS PLAN adds `--destructive: var(--status-missing)` inside EACH [data-theme] block (incl. :root/velious) so the destructive buttons are theme-consistent (UI-SPEC § Color). Heavy caveat: heavy's --status-missing is dark (#6b1a1a) → the destructive button on Heavy uses accent-colored text, not --bg text (UI-SPEC contrast note).
- Icons: @lucide/svelte (e.g. `import LogIn from '@lucide/svelte/icons/log-in'`). Already a dep. No new UI dependency (UI-SPEC Registry Safety).
- npm scripts: `npm run check` (svelte-check typecheck), `npm run build` (vite build → 200.html), `npm run test:unit -- --run` (vitest).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser DOM ← Discord username/avatar | user-controlled strings rendered in the shell + screens |
| frontend gate vs API gate | the client gate is UX-only; the server (15-02/15-03) is the authority |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-15-19 | XSS | interpolated Discord usernames | mitigate | Render usernames via Svelte `{}` (auto-escaped); NO `{@html}` on user/Discord data (the only sanctioned {@html} stays ItemTooltip's pre-escaped composeItemNote, untouched here) |
| T-15-20 | Elevation of privilege | officer-only Admin nav | mitigate (UX) + defer to server | Layer 1: the Admin nav + /admin links render only when session.isOfficer (client suppression); Layer 2 (authoritative): the server re-checks officer status on every admin endpoint (15-03) — the frontend MUST treat a 403 as "not an officer" and collapse the Admin UI, never trust the hidden nav |
| T-15-21 | Spoofing | stale authorized UI after the server says no | mitigate | A 401 from any API call routes to LoginScreen; a 403 routes to the officers-only refusal — never render stale authorized UI after the server rejects (UI-SPEC "auth state is server-truth") |
| T-15-22 | Information disclosure | session cookie exposure to JS | mitigate (inherited) | The cookie is httpOnly (set by 15-02) — JS cannot read it; the client only ever sends credentials:'include' and reads the whoami-web JSON, never the cookie value |
</threat_model>
