## Milestone Goal

Associate SquireBot users with specific characters, let them view those characters' inventory, and create character-tagged wantlist items that roll up to the guildwide wantlist.

**Goal MET:** all three delivered, deployed live (schema v10), and browser-smoke verified; the v2.3 milestone audit PASSED 2026-06-09 (14/14 requirements · 3/3 phases · 6/6 integration · 3/3 flows).

## Scope

Backend (`internal/backendsrv`) + web (`web/`) ONLY. The Go **watcher is UNTOUCHED** — backend-only schema change; **no `WatcherMaxSchemaVersion` concern**. Two additive goose migrations: `00009` (P26 `character_assignment`) → schema v9, and `00010` (P28 wantlist `character_id`) → schema **v10** (both extend-only, version-stamped, idempotent; `character_id` on `wantlist_item` is NULLABLE — existing wants backfill to NULL with no data loss).

**Builds on (verified in code, did not rebuild):** `character.owner_id → owner.discord_user_id → web_user` already links each character to one upload-owner; v2.3 added the explicit claim/assign surface. Read views stay **all-members consolidated** (CLAUDE.md LOCKED) — MYVIEW is an ADDITIVE filter, NOT access control. `wantlist_item` (00006) is per-user; v2.3 added the optional character dimension. The EC-tunnel monitor (`internal/backendsrv/ec`) still DMs the **owner** (notifications key on `discord_user_id`).

## Locked Decisions (2026-06-08)

- **Assignment = BOTH** member self-claim (incl. characters under an unlinked/legacy owner) AND officer assign/override/reassign. Single-assignee primary key on `character_assignment`; bank/bot designation is **officer-only**.
- **Inventory = ALL-MEMBERS + FILTER** — keep the all-members consolidated views, ADD a "my characters" filter/drill-down. ADDITIVE — not an access-control restriction.
- **Wantlist = CHARACTER-TAGGED** — wants gain an optional character dimension and aggregate into the guildwide wantlist; the EC-monitor DM still targets the character's OWNER.

**Resolved open sub-decisions (locked 2026-06-08):**
- **ASSIGN-05** — single-assignee model (single-assignee PK on `character_assignment`); shared bank toons handled via officer-only bank/bot designation rather than multi-owner rows.
- **CWANT-04** — the guildwide wantlist SHOWS per-want character + owner (`web_user.username`) attribution, EXCLUDING the private `note`.
- **CWANT-05** — the EC-monitor embed NAMES the character via a display-only "For <char>" field; the DM target stays the owner `discord_user_id` (structurally unchanged — the owner-DM invariant is preserved).

**Execution order:** strict dependency chain — **26 → 27 → 28**. The character-assignment data layer (P26) is the foundation BOTH the my-characters filter (P27) and the character-tagged wantlist (P28) build on.

## Phases

### Phase 26: Character Assignment — ✅ 2026-06-08
**Goal:** Members can self-claim the characters they play (including ones uploaded under an unlinked/legacy owner) and officers can assign/override/reassign any character from the admin panel — backed by a versioned, audited assignment data layer.
**Requirements:** ASSIGN-01, ASSIGN-02, ASSIGN-03, ASSIGN-04, ASSIGN-05, ASSIGN-06
**Success criteria (all met):**
1. A signed-in member sees "My characters" and can self-claim a character (incl. one under an unlinked/legacy owner, or unassigned) (ASSIGN-01, ASSIGN-02).
2. A member can release/unclaim a character they hold, returning it to unassigned (ASSIGN-03).
3. An officer can assign any character to any member, and reassign/override, from the admin panel — officer-gated, IDOR-safe (ASSIGN-04).
4. The model supports the shared-bank-toon case per the ASSIGN-05 single-assignee decision without a schema rework (ASSIGN-05).
5. Every assignment change is recorded in the audit log (actor, character, action, time) (ASSIGN-06).
6. The `00009` migration applies idempotently, stamping schema v9 and adding the `character_assignment` layer without disturbing existing data.
**Plans (3):**
- 26-01 — migration `00009` (`character_assignment` single-assignee PK + `assignment_request` + `character.is_guild_bot`, idempotent auto-seed) + store layer (claim/release/request/officer/designate + reads) + relaxed single-bank invariant (5-arg `SetCharMetaTx`).
- 26-02 — backend API: member claim/release/request (RequireSession, IDOR-safe) + officer assign/reassign/remove/approve/deny/designate (RequireOfficer + in-tx `IsOfficerTx`) + 12 routes + char-meta de-bank-toon + audit.
- 26-03 — web UI: `api.ts` wrappers + "My characters" member panel/route/nav + officer assignment admin section + `CharMetaForm` bank-toon removal.

### Phase 28: Character-Tagged Wantlist — ✅ 2026-06-09
**Goal:** Wants gain an optional character dimension — a member can tag a want to one of their assigned characters, those wants roll up into the guildwide wantlist alongside untagged wants, and the member can filter/group their own wantlist by character — while the EC-tunnel monitor DM still targets the character's OWNER.
**Requirements:** CWANT-01, CWANT-02, CWANT-03, CWANT-04, CWANT-05, CWANT-06
**Success criteria (all met):**
1. A member can OPTIONALLY tag a want to one of their assigned characters; account-level and all pre-existing wants stay valid — the `00010` migration backfills existing rows to NULL `character_id` with no data loss (CWANT-01, CWANT-02).
2. Character-tagged wants aggregate ("filter up") into the guildwide wantlist; the guildwide list surfaces character/owner attribution (CWANT-03, CWANT-04).
3. A member can filter/group their own wantlist by character (CWANT-06).
4. The EC-tunnel monitor DM for a tagged want still targets the character's OWNER (keys on `discord_user_id`); the embed names the character via a display-only "For <char>" field (CWANT-05).
**Plans (3):**
- 28-01 — migration `00010` (nullable `character_id` + `COALESCE(character_id,-1)` dedup-index rewrite) + store (`AddWantTx`/`ListOwnWants` +char, NEW `ListGuildWants`) + `IsCharAssignedToTx` IDOR guard + `ErrCharNotAssigned`.

## Milestone Summary

**Key accomplishments:**
1. **Character assignment, live** — members self-claim/release the characters they play (including ones uploaded under an unlinked/legacy owner); officers assign/reassign/remove + approve/deny requests + designate bank/bot characters from the admin panel. Backed by the `00009` migration (schema v9): `character_assignment` (single-assignee PK), `assignment_request`, `character.is_guild_bot`, idempotent auto-seed; every change audited.
2. **"My characters" inventory filter** — an additive client-side quick-filter + single-character drill-down over the existing all-members consolidated views, with all-members visibility preserved (consolidated-views architecture rule LOCKED and intact — zero backend change).
3. **Character-tagged wantlist** — wants gain an optional character dimension (`00010` migration → schema v10; nullable `character_id` with COALESCE-keyed dedup, existing wants backfill to NULL with no data loss); tagged wants roll up into the guildwide wantlist with per-want character + owner attribution (private `note` excluded); members can filter/group their own wantlist by character.
4. **Owner-DM invariant preserved** — the EC-tunnel monitor still DMs the want's OWNER (`discord_user_id`); the P28 LEFT JOIN supplies only the display "For <char>" embed field. `wantmatch.Hit.DiscordUserID` is the want creator regardless of who the tagged character belongs to.
5. **IDOR-guarded tagging** — `AddWantHandler`'s `IsCharAssignedToTx` reads P26's `character_assignment` table; a forged tag (tagging a character not yours) returns 403; the tag `<select>` only ever offers the caller's own characters.

**Key decisions:** single-assignee PK on `character_assignment` + officer-only bank/bot designation (ASSIGN-05); the my-characters view is an ADDITIVE filter, NOT access control (consolidated-views rule preserved); character-tagged wantlist with `COALESCE(character_id,-1)` dedup + `IsCharAssignedToTx` IDOR guard + owner-DM invariant; migrations `00009` + `00010` → schema **v10**; watcher untouched (backend + web only).

**Cross-phase integration (audit verdict CLEAN, 6/6 wired):** P26 → P27 (`fetchMyCharacters()` is the single authoritative source feeding `myview.ts`); P26 → P28 (the tag `<select>` sources only `fetchMyCharacters()`; `IsCharAssignedToTx` reads P26's table; forged tag → 403); the owner-DM invariant holds in code.

**Carry-forward fix (999.33, quick `260609-d2o`):** the original P26 officer panel was a one-way door — `DesignateCharTx` clears the `character_assignment` row, so a bank/bot-designated character dropped out of `ListAllAssignments` (the only list the admin panel rendered) AND was excluded from member-claimable, making bank/bot a UI dead-end reachable only via direct API/DB. **RESOLVED + DEPLOYED LIVE 2026-06-09** (commits `b7b0a48`/`2b18d65`; binary + web swap, new route 401-gated): added a `ListDesignatedChars` read + `GET /api/v1/admin/characters/designated` (officer-only) + a "Designated characters / Clear designation" section in `AssignmentAdminPanel`, so an officer can return a bank/bot char to `mode:none` from the UI. The data layer was always correct/reversible — purely a UI reachability gap.

**Known deferred items (999.34 — cosmetic LOWs/NITs, non-blocking, from `28-REVIEW.md` + the v2.3 audit):** a forged-tag 403 surfaces a generic add-form error (reachable only via a tampered request); account-level adds write `"character_id":null` into the audit detail (cosmetic noise); minor naming/comment nits; plus two deferred UATs that need specific account states (the Phase 27 zero-claimed-characters hint affordance + the Phase 26 non-officer `/admin` 403 collapse — both logic/server-gate code-verified) and the organic EC-embed confirmation (no tagged item hit the tunnel in the UAT window; embed path unit-tested). None affect correctness, security, or data — batch-fix in a future polish pass.

**Requirements coverage:** 14/14 (ASSIGN-01..06 → P26 · MYVIEW-01/02 → P27 · CWANT-01..06 → P28) — all satisfied + UAT-verified. See [`v2.3-REQUIREMENTS.md`](v2.3-REQUIREMENTS.md) for the full reconciliation and [`v2.3-MILESTONE-AUDIT.md`](v2.3-MILESTONE-AUDIT.md) for the audit.
