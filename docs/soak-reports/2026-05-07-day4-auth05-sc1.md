### Architectural barriers (why the live test was structurally infeasible)

**Barrier 1 — Google Sheets quotas are per-(project, user), not just per-user.** OAuth Playground tokens authorize against the Playground's GCP project (~60/min shared quota). The watcher's tokens authorize against SquireBot's GCP project (~300/min independent quota). The two storms run in completely isolated quota buckets. To throttle the watcher externally you'd need to extract its DPAPI-encrypted refresh token from wincred and storm under SquireBot's own client_id+secret+PKCE — significant infrastructure for marginal SC-4 value over the unit suite.

**Barrier 2 — Watcher mutex serializes all batchUpdates (Plan 02-03 Pitfall D fix).** The `*Client` helpers funnel every `batchUpdate` through a single mutex. 30 simultaneous fsnotify events became 30 sequential mutex-acquired uploads at ~2.4 sec each. Effective rate at peak: ~25 calls/sec, well below Google's ~5/sec sustained per-user quota. The mass-fixture-drop fails because the mutex prevents the very burst that would self-trigger the throttle.

### Findings — drive.file write-access propagation delay

This soak surfaced a Google-side behavior the original runbook did not anticipate: after a successful Reauthorize+picker, `Spreadsheets.Get` (read) succeeds immediately under the new grant, but `spreadsheets.values.batchUpdate` (write) returns 401 for an extended period while Google propagates the new grant's drive.file write registration to all Sheets API servers.

Observed propagation window today: **51 minutes** (picker complete 15:45:57Z → first successful write probe 16:37:23Z, 50 probe attempts at 60s intervals).

A second cycle earlier in the day showed propagation completed somewhere between 25 and 56 minutes after picker (probe attempts 1–25 still failing at 25:23 elapsed; cold-start catch-up succeeded at 56:00 elapsed).

### Fix landed during soak

Three commits on `master` extended AUTH-05 handling for the propagation delay:

- `9ba1759` — `fix(auth): add picker phase to Reauthorize to re-register workbook under new drive.file grant`
- `c9aef96` — `fix(auth): probe batchUpdate write access in onRefresh after reauth` (superseded by next)
- `304b8bb` — `fix(auth): move drive.file propagation probe to background goroutine`

Final design (`304b8bb`): `runPostReauthProbe` runs in a goroutine outside `batchMu`, calls `PingWriteNoLock` (empty batchUpdate, no mutex acquisition) every 60s with a 90-minute timeout. While the probe is running, `globalAuthSuspended` keeps watcher events from queueing on `batchMu`; the tray stays green with status "Reauthorized: waiting for Google propagation…" and the Reauthorize menu item stays hidden. On probe success, the suspension is cleared and uploads resume on the next file event.

The 90-minute timeout had ~40 minutes of headroom against the observed 51-minute propagation. If real-world propagation ever exceeds 90 minutes, the timeout surfaces a Reauthorize prompt as a last resort.
