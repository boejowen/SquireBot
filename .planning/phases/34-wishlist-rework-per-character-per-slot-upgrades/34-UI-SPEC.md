# Phase 34 — UI Design Contract

> Visual and interaction contract for the SquireBot web app's **per-character, per-slot upgrade
> Wishlist** (WISH-01..07) — the guild-wide answer to *"what can I get to improve my characters?"*.
> Generated by gsd-ui-researcher.
>
> **This is a NEW data surface inside an existing, already-LOCKED visual language** — five EQ
> themes, `[data-theme]` single source of truth, established tokens and component idioms (Phase
> 14/30/31/32/33 UI-SPEC lineage). This spec **invents no palette and no new pattern.** The
> Wishlist tab is, structurally, **the Phase-32 Inventory tab re-skinned to characters + a per-slot
> upgrade-target detail**: it reuses the P32 `/inventory` master-detail shape **verbatim** (the
> two-pane grid, the scoped search visual, `StateBlock` states, the bespoke selectable-row list),
> the P31/P32 `RosterFor` viewer-first character list **verbatim** (WISH-01, MINUS the bank band),
> the P31 `ExaminePanel` **verbatim** (WISH-06), the v2.2 wantlist **ping/mute bell + `Toggle`** for
> the per-target ping toggle (WISH-05), the v2.2 `WantAddForm` debounced catalog/custom add pattern
> for the typed-entry affordance (WISH-03), and the P33 `LastSyncedCell` for the suggestion's
> last-listed freshness. The only genuinely new pieces are (a) the **per-slot accordion** of the ~21
> P31 worn slots, each with its equipped-item header (D-04 — ALL worn slots, even empty), (b) the
> per-slot **wishlist-target rows** (name + price + wiki + last-listed + "Raid" tag + ping toggle +
> EC-hit badge + examine), (c) the per-slot **suggestion picker** seeded from `_wiki_gear_tier`
> (WISH-04), and (d) the cross-wishlist **search** (WISH-07). Locked decisions **D-01..D-04** +
> **WISH-01..07** + the carried-forward P31/P32/P33 idioms are encoded here, not re-litigated.
> **This is a structure/data revamp, NOT a re-skin** — the live 5 EQ themes render unchanged.
>
> **Distinguishing trait vs. P32/P33:** the Inventory and Banks tabs are read-only browse/select
> surfaces. The Wishlist is the FIRST v2.4 tab with **mutating, owner-scoped writes** — add a
> target, remove a target (destructive), toggle a ping. Those writes follow the v2.2 wantlist
> server-truth discipline (NEVER optimistic-mutate; add/remove/toggle ALWAYS re-fetch the
> authoritative wishlist), and the remove gets a `ConfirmDialog` (the v2.2 wantlist-remove pattern).

## Spacing Scale

The codebase uses a strict 4-based scale (verified in `SiteShell`, `StateBlock`, `/inventory`,
`/characters`, `ExaminePanel`, `WantlistPanel`). Reuse it **exactly** — introduce no new spacing
values. Values below are **lifted verbatim from `/inventory/+page.svelte`** (the direct
master-detail analog) so the four v2.4 tabs are pixel-consistent.

| Token | Value | Usage in this phase |
|-------|-------|---------------------|
| xs | 4px | Inline gap inside a target-row headline (price ↔ last-listed ↔ tag); the equipped-item line's icon-omitted inline rhythm; the suggestion-row meta gap |
| sm | 8px | Character-list row inner gap; search ↔ hint gap; per-slot header inner gap; target-row inner gap; ping-toggle ↔ label gap (the `Toggle` default); add-control field gap |
| md | 16px | Character-list row horizontal padding (`8px 16px`); search input inner padding; per-slot section vertical padding; target-row horizontal padding; section → section gap; mobile gutters |
| lg | 24px | The two-pane column gap (list column ↔ detail column) — **identical to `/inventory` + `/characters` `gap: 24px`**; the per-character detail header → first slot section gap; the accordion-section → accordion-section gap |
| xl | 32px | Page horizontal gutters (desktop — inherited from `shell-main`) |
| 2xl | 48px | Empty/no-results vertical centering block (reuses `StateBlock` `padding: 48px 16px`); the "pick a character" detail prompt; the "no targets yet" empty-wishlist block |

**Touch-target exception (existing rule, non-negotiable):** every interactive affordance — a
character-LIST row, the search input, a per-slot section HEADER (if the accordion is
collapse/expand), a wishlist-TARGET row's interactive parts (the ping `Toggle`, the remove button,
the examine trigger, the wiki/PigParse links), an ADD-control field, a SUGGESTION row — has an
effective hit area `>= 44px`. A character-list ROW is `min-height: 44px` (same as `/inventory`
`.row`). The ping `Toggle` is already `min-height: 44px` (its own spec). The remove button is
`min-height: 44px`. A suggestion row (the add affordance) is `min-height: 44px` (the `WantAddForm`
`.result-pick` precedent). Gutters collapse to **16px** below 640px (inherited `shell-main` /
SiteShell `@media (max-width: 640px)` rule — keep it).

**No item-icon tiles in the character list OR the target rows.** Unlike the P32 item list (32px
tile), this tab's character-list rows show **name + level/race/class meta only** (the `/characters`
row treatment verbatim), and the per-slot target rows are **text rows** (name + price + wiki +
last-listed + tag + toggle), NO icon tile. Item icons appear ONLY inside the reused `ExaminePanel`
on examine (WISH-06) — and `ExaminePanel` renders no icon itself, so this tab carries **zero**
remote item-icon `<img>`. (This keeps the per-slot accordion dense and scannable; the icon is a
detail-on-examine affordance, not a per-row decoration.)

Exceptions: none beyond the inherited mobile gutter collapse + the reused `Toggle`'s internal 40×22
track (within-component, not a layout gap).

## Typography

Roles are already declared across the live UI-SPEC lineage (14/30/31/32/33) and rendered in
`SiteShell` / `StateBlock` / `ExaminePanel` / `/inventory` / `/characters` / `WantlistPanel`.
**Reuse verbatim — this phase adds NO new type roles.** The reused `ExaminePanel` and `Toggle`
carry their own already-locked typography — do not re-specify them.

| Role | Size | Weight | Line Height | Where in this phase |
|------|------|--------|-------------|---------------------|
| Body | 16px | 400 (`--font-body`) | 1.5 | Character name in a list row, the equipped-item name, target-row item name, suggestion-row item name, search input text, hints, the per-character detail-header meta, all prose |
| Label | 13px | `--weight-display` | 1.2 | The character-list row meta tag ("you"); the per-slot section eyebrow (slot name); the equipped-item "EQUIPPED" eyebrow; the "Raid" tag; the suggestion eyebrow ("PRE-RAID / GROUP" / "RAIDING"); the ping `Toggle` word (ON/OFF, reused); the "not for sale" annotation; the search hint; the EC-hit badge text |
| Heading | 20px | `--weight-display` | 1.2 | The per-character detail-header character NAME (matches `/inventory` `.detail-name` = 20px accent); the "Pick a character" / "No targets yet" prompt headings |
| Display | 24px / 28px → reuse | `--weight-display` | 1.2 | **Not introduced this phase.** The only 24px is the reused `ExaminePanel`/window roles; the 28px wordmark stays in `SiteShell`. No new Display use here. |

**Character-list row typography (WISH-01 — `/characters` `.row` verbatim):**
- Character **name** = Body 16px in `var(--text)` (MAY use `--font-display` to echo the EQ
  char-name feel, matching `/characters` `.row-name` — stay on 16px).
- A small accent **"you"** Label tag on the viewer's own characters (the `/characters` `.tag`
  treatment). **No "bank"/"bot" tags** — WISH-01 EXCLUDES banks/bots from the list entirely, so
  those bands/tags never appear here.
- The dimmed meta line `Level {n} {race} {class}` = Body 16px `var(--text)` `opacity: 0.85` (the
  `/characters` `metaLine` idiom — drop a zero level / blank race / blank class token, never
  "Level 0", D-11 carry-forward).

**Per-slot section typography (WISH-02 / D-04):**
- The **slot name** (the section header) = Label 13px `--weight-display`, uppercase,
  `letter-spacing: 0.05em`, `color: var(--accent)` (the `holders-eyebrow` / `band-label` idiom).
  The ~21 worn slots are the P31 paperdoll taxonomy (see §Layout B).
- The **equipped item** line = an "EQUIPPED" Label eyebrow (13px dimmed) + the item NAME at Body
  16px `var(--text)`; when the slot is empty (D-04), the line reads "Empty" at Body 16px dimmed
  (`opacity: 0.7`) — never blank/"null". The equipped item is itself examine-able on hover/tap
  (WISH-06).

**Wishlist-target row typography (WISH-03/04/05/06 — the load-bearing row):**
- Target **item name** = Body 16px `var(--text)` (MAY use `--font-display` to echo the EQ
  item-name feel — stay 16px).
- **PigParse price** = Body 16px, `color: var(--status-other)`, `font-variant-numeric:
  tabular-nums`, rendered as `{value}pp`; OMITTED entirely when no price resolves (D-09 carry —
  never "—"/"null"). The "not for sale" items (WISH-04 no-drop/raid-only) render NO price and the
  Label annotation "Not for sale" (dimmed) in the price slot's place.
- **Wiki link** = `var(--accent)` + 1px accent underline + trailing `↗` ("Wiki ↗"), the live
  `/inventory` `.row-wiki` idiom; links to the P1999 wiki page.
- **Last-listed date** = the reused `LastSyncedCell` (a freshness dot + the YYYY-MM-DD date),
  semantically "when this item was last seen for sale on PigParse" — the same name-keyed
  last-listed P29 value the examine uses. (A target with no recorded listing omits the cell, D-09.)
- **"Raid" tag** = a small Label (13px `--weight-display`, uppercase), `color: var(--status-other)`
  (the `WantAddForm` `.custom-chip` chip idiom — NOT accent; accent is reserved). Present only on
  no-drop/raid-only suggestions (WISH-04).
- **Ping toggle** = the reused `Toggle` (role="switch", ON/OFF word) — its typography is locked.
- **EC-hit badge** = a Label (13px `--weight-display`), accent text on a faint accent wash
  (`color-mix(in srgb, var(--accent) 8%, transparent)`) — text "Seen in EC" (see §Color +
  §Copywriting); the badge carries a `title`/`aria-label` with the hit timestamp.

**Per-character detail-header typography (WISH-02):**
- The character **NAME** = Heading 20px accent (`/inventory` `.detail-name` verbatim).
- The **meta line** = `Level {n} {race} {class}` at Body 16px dimmed (`opacity: 0.85`) — the
  `metaLine` idiom (show what's known, never "null", D-11).

**Suggestion-picker typography (WISH-04):** the suggestion eyebrow (the tier band) = Label 13px
accent uppercase; the suggestion item name = Body 16px (`--font-display` ok); its price/wiki/
last-listed/Raid-tag use the SAME treatments as a target row (above) — a suggestion reads as a
"not-yet-added target". The typed-entry field = the `WantAddForm` search field (Body 16px, accent
focus ring).

## Layout & Interaction Contract

> This is the load-bearing section. The tables above are tokens; this is the structure the executor
> builds. The canonical visual reference is the **already-shipped `/inventory` + `/characters`
> master-detail** — this tab MIRRORS that approved two-pane shape so Wishlist + Inventory + Banks +
> Characters feel identical, with the RIGHT column being a per-character per-slot accordion instead
> of a holders table or a paperdoll window.

### A. Route & page frame

- The Wishlist tab is the route `/wishlist` (it **replaces** the Phase-30 `/wishlist` placeholder —
  the current `WantlistPanel` + Notifications rehome — with the real per-character per-slot
  wishlist). The Phase-30 alert badge + notifications still live on this tab (D-03 / P30
  carry-forward): the notifications region MAY remain on the page (planner's discretion on its
  placement — below the two-pane, or folded into a settings affordance) OR be relocated per the
  planner; the contract is that the per-character wishlist is the tab's PRIMARY content and the
  notifications inbox/badge stay reachable on this tab. The `NotificationInbox` keeps owning its own
  badge refresh — this page must NOT import or mutate the badge store (the P30 §4 gotcha).
- `/wantlist` **308-redirects to `/wishlist`** (D-03) — already shipped in `web/src/routes/wantlist/
  +page.ts`; keep it. The old `WantlistPanel`-based `/wishlist` body is REPLACED by this design.
- The tab mounts inside the Phase-30 `SiteShell` (5-tab strip already present; `/wishlist` tab gets
  `aria-current="page"` automatically).
- **Master-detail on ONE route (no per-character route explosion).** The CLAUDE.md consolidated-
  views lock is RELAXED for exactly this pattern (ratified 2026-06-17): ONE reusable detail (the
  per-character per-slot accordion) rendered for the SELECTED character. Selection MAY be reflected
  in the URL (`/wishlist?c=<charName>`) so a character's wishlist is deep-linkable/shareable —
  **planner's discretion**; mirror the `/characters` `?c=` / `/inventory` `?i=` seam via

  that selection renders the single reusable detail, not N materialized routes.
- **Two-pane shape (desktop):** `grid-template-columns: minmax(280px, 360px) 1fr; gap: 24px;
  align-items: start;` — **identical to `/characters`** (character names are short like the
  characters tab, so the 280–360px list column matches `/characters`, NOT the wider `/inventory`
  300–380px). When no character is selected, the detail column shows a "Pick a character" prompt
  (§I). On mobile the panes stack (§E).

### B. The character list (WISH-01)

**One row per non-bank/non-bot character, viewer's-first-then-A-Z (WISH-01).** The list is the
`RosterFor` viewer-first roster **MINUS the banks/bots band** — WISH-01 explicitly excludes guild
banks and bots (you don't wishlist for a bank). Reuse the `roster.ts` `filterRoster` / `viewerFirst`
helper, then **drop the `banks` band** (the rows where `is_bank_toon || is_guild_bot` and NOT
`is_mine`). A viewer's OWN bank toon: per `bandOf`, `is_mine` wins the tie-break, so a viewer-owned
bank toon would rank in "mine" — but WISH-01 is "banks/bots EXCLUDED", so the cleanest contract is
**exclude any `is_bank_toon || is_guild_bot` row regardless of `is_mine`** (a bank toon has no worn
paperdoll to upgrade). Planner: confirm the exclusion predicate (recommended: exclude
`is_bank_toon || is_guild_bot` outright). The remaining list is **two bands** — YOUR CHARACTERS,
then GUILD — A-Z within each (the `/characters` band idiom minus the third band), OR a single
viewer-first-then-A-Z run with NO band labels (planner's discretion; the `/inventory` single-run
treatment is also acceptable since there are now only two bands). Default recommendation: keep the
two band labels (YOUR CHARACTERS / GUILD) for parity with `/characters`.

**Row treatment (bespoke — mirror `/characters` `.row`):**
- A selectable `<button type="button">` per character, `min-height: 44px`, `--panel` background,
  `padding: 8px 16px` (sm × md), a 1px `--border` bottom separator, a `3px transparent` left border
  that turns `--accent` when selected.
- Layout (mirror `/characters` `.row` — column body, no icon tile): the character **name** + an
  accent "you" tag on the viewer's own rows (the lead line); the dimmed `Level {n} {race} {class}`
  meta line below (D-11 — show what's known, never "null").
- **Selected state:** the accent left-border + accent character-name + `aria-pressed="true"`.
  Exactly one row selected when a character is shown.
- Hover: `background: color-mix(in srgb, var(--accent) 8%, transparent)`. Focus-visible: `outline:
  2px solid var(--accent); outline-offset: -2px`.

### C. Per-tab scoped search (WISH-07)

The search bar lives at the **top of the list column** (the `/characters` / `/inventory`
placement), reusing the search visual **VERBATIM** (`/inventory` `.search`: flex row, `--panel`,
`border: 1px solid var(--border, var(--accent))`, `border-radius: 4px`, `min-height: 44px`,
`padding: 8px 12px`, a leading `Search` lucide glyph 16px `aria-hidden`, Body 16px text;
`:focus-within` → `border-color: var(--accent)`; `:focus-visible` → `outline: 2px solid
var(--accent)`).

**The WISH-07 search is BROADER than a character-name filter.** WISH-07: "a wishlist search over all
items on any wishlist + the non-bank/bot characters." So a query matches BOTH (a) **character names**
(filtering the list to characters whose name matches) AND (b) **wishlist targets** (any item on any
character's wishlist whose name matches the query, across all non-bank/bot characters). Resolve this
for the contract as a **two-section results list in the left column when a query is active** (mirror
the P33 list⇄item-search toggle — the search OWNS the left column while active):

- **Empty query → CHARACTER LIST mode (§B):** the left column shows the viewer-first character list.
- **Non-empty query → SEARCH-RESULTS mode:** the left column REPLACES the character list with two
  labelled result groups:
  1. **CHARACTERS** — matched non-bank/bot characters (viewer-first), each a selectable row that
     pins that character's wishlist in the right column (same `select(char)` the list rows call).
  2. **WISHLIST ITEMS** — matched wishlist targets across all non-bank/bot characters, grouped by
     item name, each result naming **which character(s) wishlist it** (and on which slot); clicking
     a result pins THAT character's wishlist in the right column and (planner's discretion) scrolls
     to / expands the matching slot section. This is the WISH-07 "all items on any wishlist" leg.

### F. The suggestion picker (WISH-04)

Per slot, the add control surfaces the **COMPLETE** Velious Pre-Raid/Group + Raiding suggestions for
THIS character's class + THIS slot, from the existing `_wiki_gear_tier` data (the same table
`compute/gearcheck.go` reads):

- **Mapping:** the character's class (from `store/charmeta.go` `CharMeta.class`) + the per-slot
  worn-slot token → the wiki gear-tier rows. The wiki gear-tier pages use PROSE slot labels (Ears,
  Fingers, Wrists, Head, ...); the paperdoll uses inv-slot tokens (EAR1/EAR2, ...). Reuse
  `enrich.WIKI_SLOT_TO_INV_SLOTS` (the gearcheck.go seam) to map: a paperdoll section (e.g. Ear1)
  maps to the wiki slot whose inv-slot list contains its token (Ears → EAR1/EAR2). So both Ear1 and
  Ear2 sections surface the same "Ears" suggestions; both Wrist1/Wrist2 → "Wrists"; both
  Finger1/Finger2 → "Fingers" (planner: confirm the reverse-map direction). Slots with no wiki
  gear-tier mapping (e.g. Ammo, Range for some classes) simply show no suggestions — only the typed-
  entry path (WISH-03).
- **Display:** the suggestions are a **flat complete list** under two tier eyebrows — "PRE-RAID /
  GROUP" and "RAIDING" (Label accent eyebrows, the `alwaysShownTiers` order). NO Group/Raid binary
  tiering (deferred — WISH-04 explicitly: a flat complete list with a "Raid" tag, NOT a Group/Raid
  split). Each suggestion is a row (§E anatomy): name + PigParse price + Wiki link + last-listed
  date + a "Raid" tag (no-drop/raid-only) + an **Add affordance** (a `+`/"Add" button, the
  `WantAddForm` `.result-pick` idiom — one-click adds it as a target for this character+slot;
  server-truth: POST then re-fetch). A suggestion the character ALREADY HAS, or that's already a
  target, is hidden/marked-added (planner's discretion — recommended: hide already-equipped per D-02,
  mark already-added).
- **"Raid" tag + "not for sale" (WISH-04):** no-drop/raid-only suggestions carry the "Raid" Label tag
  and render NO price ("Not for sale" annotation). **Data note (planner — load-bearing):** the
  `_wiki_gear_tier` store row (`store.WikiGearTierRow`) currently carries `{Tier, Class, Slot,
  ItemName, ...}` and does NOT persist a no-drop flag — the TS parser derives `is_no_drop` but

  therefore a planner/researcher data seam: either (a) the no-drop flag is sourced from the
  `item_master` enrichment (which parses `is_no_drop`), joined by name, OR (b) "Raid"/not-for-sale
  is inferred from the tier ("Velious Raiding" tier ⇒ raid-only) — planner's call. The UI contract is
  fixed: a no-drop/raid-only suggestion shows the "Raid" tag + "Not for sale" (no price); a
  group/for-sale suggestion shows its PigParse price. Do NOT invent a tag the data can't back.

## Accessibility Contract (load-bearing — mirror `/inventory` §G + the v2.2 Toggle/ConfirmDialog a11y)

1. **Character-list rows are buttons.** Each row is a `<button type="button">` with an accessible
   name = the character name (+ "you"/level/race/class context). `aria-pressed` reflects selection;
   exactly one pressed when a character is shown.
2. **Per-slot section headers** (if collapsible) are `<button>` with `aria-expanded` + `min-height:
   44px`, accessible name = the slot name + "{n} targets" / "empty".
3. **The ping toggle is a `role="switch"`** (the reused `Toggle`) with `aria-checked` + an accessible
   `label` ("Ping me when {item} appears in EC"); the visible ON/OFF word means state is never
   color-only.
4. **The remove button** is a `<button>` naming its target ("Remove {item}"); it opens a focus-
   trapped `ConfirmDialog` (the v2.2 modal a11y — Esc cancels, focus returns).
5. **The add control** (typed-entry + suggestions): the search input has an `aria-label`; each
   suggestion "Add" is a `<button>` naming the item ("Add {item}"); the custom affordance is a
   `<button>`.
6. **Keyboard:** every character-list row, slot header, target examine trigger, ping toggle, remove
   button, add field, suggestion "Add", wiki/PigParse link, and search input is Tab-reachable;
   Enter/Space activates. The wiki/PigParse links are normal focusable links (`stopPropagation` so
   they don't trigger row examine/select).
7. **Focus-visible:** every focusable affordance shows `outline: 2px solid var(--accent)` on
   `:focus-visible` (`outline-offset: 2px`, or `-2px` where it would clip a row/section edge). The
   already-shipped universal treatment; the reused `Toggle`/`ConfirmDialog`/`ExaminePanel` keep
   their own.
8. **44px touch targets:** character-list rows, slot headers, the ping toggle, the remove button, the
   add field, suggestion rows, and the search input are all `min-height: 44px`.
9. **Color is never the sole signal:** the ping state is the ON/OFF WORD (not color); the "Raid" tag,
   the EC badge, and "Not for sale" are TEXT (not color); the selected row carries `aria-pressed`
   (not only the accent border); the last-listed freshness is a dot PLUS a date label (the
   `LastSyncedCell` contract); the destructive remove is labelled "Remove" (not only `--destructive`
   color).
10. **Live regions:** the add/remove/ping announces use polite `aria-live` (the v2.2 wantlist
    announce idiom) so a screen reader hears the result of each mutation.
11. **Reduced motion:** any row-hover/transition, the accordion expand/collapse, the `Toggle` thumb
    slide, and the detail-swap honor the global `@media (prefers-reduced-motion: reduce)` rule in
    app.css (instant); the reused components already honor it.
12. **Theme-independence:** all of the above holds under all 5 themes — verify the accent focus ring +
    selected border + eyebrows + EC badge + `Toggle` ON track + `--destructive` Remove read on Heavy
    (`#f0d088` / `#e88a8a`-on-`#1a0e05`) and Minimalist (`#b8915c`); spot-check at build.
13. **The single `{@html}` sink rule (carried, T-31-14 / T-32-07):** the ONLY raw-HTML in this tab is
    `ExaminePanel`'s `composeItemNote` wiki body (already escaped + scheme-allow-listed), reused
    UNCHANGED. Character/item/slot names render via plain `{}` interpolation. This phase adds NO new
    `{@html}` sink.
