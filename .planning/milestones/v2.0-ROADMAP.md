## Overview

The milestone that took SquireBot **off Google entirely** — replacing the shared Google Sheet (both the UI *and* the data store) with a self-hosted Go + SQLite backend and a static SvelteKit web frontend, permanently eliminating the Google OAuth dependency that had walled off the guild.

**Why now:** Google's brand-verification gate rejected the v1.0.2 OAuth client on 2026-05-15 (*"home page not registered to you"* — `github.io` can't satisfy it), silently expiring the refresh tokens of all ~12 guildie watchers. Rather than rent a real domain just to placate Google (throwaway work, since the Sheet itself was the long-term liability), v2.0 removed Google from the system end to end: a Hetzner VPS backend, Discord OAuth2 login, and a per-guildie opaque bearer token for the watcher.

**Sequencing principle — FRONT-LOAD THE INGEST PATH:** the guild was dark on the Sheet for the entire build (Google walled off their watchers on 2026-05-15). So P11 (ingest endpoint) and P13 (watcher re-target) restored the data pipeline first; the polished frontend (P14), the login + officer forms (P15), and the cutover (P16) followed once data was flowing again.

**Schema-evolution change:** the old `_meta.schema_version` ↔ `WatcherMaxSchemaVersion` handshake **retired** in favour of forward-only `goose` DB migrations + an explicit **API version** (`/api/v1/...`). The watcher's Sheets schema gate was removed in P13.

**Timeline:** started 2026-05-28, shipped 2026-05-31 (4 calendar days of active work). 6 phases, 29 plans. The re-targeted watcher binary is 57% smaller (16.44 MB → 7.07 MB) and carries no Google secret. The Sheet + Apps Script (13,266 LOC TypeScript) were decommissioned in place; the watcher shed ~8k LOC of OAuth/Sheets/Picker code.

**Stack (LOCKED + costed, ≈ $67/yr total):** Hetzner Cloud shared-vCPU VPS (US, amd64) backend (~$55/yr) · SQLite + `goose` forward-only migrations ($0) · SvelteKit static (apex on Caddy) ($0) · Discord OAuth2 website login ($0) · per-guildie opaque bearer token for watcher↔backend ($0) · ~$12/yr **website-only** domain (`squirebot.quest`, registered at Porkbun — no Google verification needed). Backend hand-rolled `net/http` + `modernc.org/sqlite` (PocketBase evaluated and rejected).

**Goal**: Stand up the self-hosted backend so guildie watchers have a live, authenticated place to upload to again — Hetzner Cloud VPS (US) behind Caddy auto-HTTPS, a SQLite schema under `goose` forward-only migrations, per-guildie bearer-token auth, and the upload-receiving endpoint that atomically replaces a character's rows.
**Depends on**: Nothing (first phase of v2.0; foundation for everything after)
**Requirements**: BACKEND-01, BACKEND-02, BACKEND-03, BACKEND-04, BACKEND-06
**Success Criteria** (what must be TRUE):
  1. The backend serves over HTTPS at the website domain from the Hetzner Cloud VPS (US) — a single Go binary behind Caddy, restart-on-reboot via systemd, reachable with a valid TLS certificate (BACKEND-01)
  2. `goose up` applies the SQLite schema cleanly on a fresh database, creating separate `owner` and `character` tables plus inventory/spellbook/dimension tables; re-running it is a no-op (forward-only, idempotent) (BACKEND-02)
  3. A `POST` of a full-snapshot inventory or spellbook payload, carrying a valid `Authorization: Bearer <guild-code>`, atomically replaces that character's rows (delete-all-then-insert in one transaction) and the rows are then visible via a query — and a shrinking snapshot drops the removed rows (BACKEND-03)
  4. A request with a missing, malformed, or unknown bearer token is rejected (401) and writes nothing; the maintainer can mint a per-guildie token whose plaintext is shown once and stored only hashed server-side (BACKEND-04)
  5. A nightly off-box backup of the SQLite file runs on a schedule, and the documented restore procedure reconstitutes the database from a snapshot on a clean box (BACKEND-06)

**Requirements**: ENRICH-10, ENRICH-11
**Success Criteria** (what must be TRUE):
