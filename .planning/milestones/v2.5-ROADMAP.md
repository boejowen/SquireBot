# Milestone v2.5: Ownership Cleanup

**Status:** ✅ SHIPPED 2026-06-22
**Phases:** 35–36
**Total Plans:** 3 (35: 1, 36: 2)

## Overview

Reconcile character-ownership semantics for a guild that shares P99 logins. Two problems, both deferred from quick task `260621-u6j` (which dropped the single-owner write gate so any guildie can upload any character): (1) designated guild banks/bots were tied to whoever first uploaded them, so designation required pre-existing ownership and the per-owner eviction cascade swept a bank away when its first-uploader was evicted; (2) a *shared* non-bank character (played/uploaded by multiple guildies) was deleted when its first-uploader was evicted. Backend + a small web change; **the Go watcher is UNTOUCHED → no `v*` git tag** (consistent with v2.3/v2.4). One schema migration (`00015`, Phase 35); Phase 36 is compute-on-read with no migration. Deployed live to squirebot.quest 2026-06-22 (prod schema v14→v15 on the Phase-36 deploy boot — the first prod application of `00015`).

## Phases

### Phase 35: Owner-less guild banks & bots

**Goal**: A designated bank/bot is guild-held, not tied to whoever uploaded it first.
**Depends on**: Nothing new (builds on the live v2.0+ backend + the `260621-u6j` cross-owner-write relaxation)
**Plans**: 1 plan
**Requirements**: OWN-01, OWN-02, OWN-04

Plans:

- [x] 35-01: migration `00015_guild_owner.sql` (seed the reserved "guild" sentinel owner id `1000000` + backfill existing bank/bot chars to it) + `store/owner.go` `GuildSentinelOwnerID` + `DesignateCharTx` owner_id repoint + `ListEvictableOwners`/`ListRestorableOwners` sentinel exclusion + the OWN-02 survives-eviction proof + (code-review CR-01 fix) `EvictOwnerTx`/`RestoreOwnerTx` sentinel write-path guard

**Details:**
**RESOLVED design = Option A — a reserved "guild" sentinel owner row (id `1000000`, label `guild`), NOT a nullable `owner_id`** (smallest blast radius: `character.owner_id` stays `NOT NULL`, every existing `owner(id)` join keeps working; only 2 production consumers — binding.go + eviction.go). `DesignateCharTx` repoints `owner_id` → sentinel inside the officer-gated tx; the sentinel belongs to no guildie so it is never an eviction target. Migration `00015` seeds the sentinel (`INSERT OR IGNORE`) + an idempotent backfill (`owner_id <> 1000000` guard) repoints every `is_bank_toon=1 OR is_guild_bot=1` char (OWN-04 — Findom + Slowscales auto-migrated live with no manual fixup). **Code review caught 1 BLOCKER (CR-01):** the sentinel was excluded from the eviction *picker reads* but the destructive *write path* (`EvictOwnerTx`) had no guard — an officer POSTing `{"owner_id":1000000}` would have wiped the bank; fixed-forward with a typed `ErrCannotEvictSentinel` guard at the top of `EvictOwnerTx`+`RestoreOwnerTx` (mapped to 403). Verifier PASSED 6/6 must-haves + 3/3 req IDs. **IN-02** (a label lookup could resolve the reserved `'guild'` label — pre-existing, astronomically unlikely) deferred to backlog.

### Phase 36: Shared-character-safe eviction

**Goal**: Eviction removes only the evicted member's own characters — never shared characters that other guildies also play and upload (banks/bots already eviction-safe via Phase 35).
**Depends on**: Phase 35 (reuses the sentinel model — banks are eviction-safe by construction, so Phase 36 narrows the cascade purely for shared NON-bank chars)
**Plans**: 2 plans (backend wave 1 → web wave 2; the web change consumes the backend's new preview contract)
**Requirements**: OWN-03

Plans:

- [x] 36-01 (backend): narrowed `EvictOwnerTx` cascade + parity-locked `PreviewEviction` via a single shared `cross_owner_write` predicate (shared chars survive) + additive `preserved_shared_count` preview field + drift-locked steward repoint
- [x] 36-02 (web): mirror `preserved_shared_count` in `api.ts` + keep all-shared owners evictable in `EvictionForm.svelte` (code-only-revoke framing) via pure node-tested helpers + deploy + browser-smoke

**Details:**
"Shared" is derived from the existing `audit_log` `cross_owner_write` trail (written by `binding.go` since `260621-u6j`; Phase 36 is its FIRST reader) — NO new table, NO migration (schema stays v15). A char stewarded by evicted owner X is shared iff a `cross_owner_write` row exists with `char_name = character.name COLLATE NOCASE AND attempting_owner_id <> X`. One shared `sharedCharPredicate` const backs BOTH the cascade UPDATE and `PreviewEviction` (D-04 parity — the explicit lesson from Phase 35's CR-01: the preview removed-set == the cascade removed-set, can't diverge). The guild-code revoke stays unconditional on `removedCount` (an owner who only stewards shared chars → 0 removed but code still revoked). **Plan-checker caught 1 BLOCKER:** narrowing the preview EMPTIES it for an all-shared owner → `EvictionForm.svelte` disabled the Evict button → that departing member's code couldn't be revoked. **User RATIFIED expanding scope backend→backend+web:** additive `preserved_shared_count` + the web form keeps an all-shared owner evictable (code-only-revoke framing). Code review 0 BLOCKER (2 non-blocking WARNINGs backlogged: WR-01 preview guard asymmetry [pre-existing]; WR-02 cosmetic repoint-to-evicted-steward). Verifier PASSED 13/13. **Deployed live + officer browser-smoke APPROVED.**

## Milestone Summary

**Decimal Phases:** None.

**Key Decisions:**

- **Sentinel owner over nullable owner_id (Phase 35, Option A)** — Rationale: `character.owner_id` is `NOT NULL` in 00001; nullable would require a 12-table CASCADE-FK rebuild + teaching every consumer to handle NULL. A real sentinel row keeps every FK/join working; the change is one additive migration + one resolver + one repoint line + two eviction exclusions. ✓ Good.
- **Derive "shared" from the existing audit_log trail, no new table (Phase 36, D-01)** — Rationale: `cross_owner_write` already records every cross-owner upload; reusing it kept Phase 36 migration-free. ✓ Good.
- **One shared SQL predicate backs both the cascade and the preview (Phase 36, D-04)** — Rationale: the direct application of Phase 35's CR-01 lesson (read path and write path must not diverge); makes preview/action drift structurally impossible. ✓ Good.
- **Expand Phase 36 backend-only → backend+web (user-ratified mid-plan)** — Rationale: the plan-checker proved the all-shared-owner edge case can't be delivered without a web change; the "all-shared owner stays evictable" requirement was load-bearing. ✓ Good.

**Issues Resolved:**

- The Findom/Slowscales bank mis-binding (banks tied to an individual first-uploader) — root cause eliminated for all designated banks/bots via the sentinel model; both auto-migrated live by `00015`.
- CR-01 (Phase 35): the destructive eviction write path was bypassable for the sentinel — fixed before the phase closed.
- The all-shared-owner UI gap (Phase 36): narrowing the preview disabled the Evict button — fixed end-to-end (backend signal + web gating).

**Issues Deferred (to backlog):**

- **P36 WR-01** — the eviction *preview* handler doesn't mirror the evict *action*'s floor/sentinel guards (read-only info-disclosure; pre-existing).
- **P36 WR-02** — the D-03 steward repoint can hand a surviving shared char to an already-evicted steward (cosmetic; `owner_id` is non-binding and survival is guaranteed; a fix would diverge the subquery from `sharedCharPredicate`).
- **P35 IN-02** — a label-bridge lookup could resolve the reserved `'guild'` label (astronomically unlikely — requires a guildie literally named "guild").
- **v2.4 MD-01** (carried) — `web/src/lib/api.ts` still has orphaned wantlist fetch wrappers → deleted routes + the WantAddForm/WantMuteCell cluster + a stale test; a good `/gsd-quick`.

**Technical Debt Incurred:** None material. Detection scans `audit_log` by `char_name` (TEXT, unindexed), but evictions are rare officer actions over a ~12-person guild — an index is unwarranted.
