# BUG: Wizard completion doesn't trigger watcher startup

**ID:** BUG-001
**Discovered:** 2026-05-09 (during first-guildie install validation on dev box, post-v0.2.0 release)
**Reporter:** Joe Bowen (boejowen)
**Severity:** HIGH (every first-time installer hits this)
**Status:** ✅ RESOLVED 2026-05-09 — fixed in commit `71f7b76`, shipped in v0.2.1
**Affects:** v0.2.0; likely also v0.2.0-rc1 and v0.2.0-rc2 (not retested)
**Fixed in:** v0.2.1 — `internal/wizard/server.go` `handleEQFolderConfirm` now calls `signalDone(res)` immediately after `cfg.Save()` succeeds, before the redirect to `/done`. Wizard completion is now independent of `done.html`'s setTimeout-driven `/wizard/shutdown` POST. The old completion path is preserved as an idempotent no-op safety net (sync.Once protection in signalDone). Two new tests in `internal/wizard/server_test.go` defend against regression.

## Symptom

After completing the first-run setup wizard (Google OAuth → workbook picker → EQ folder confirmation), the SquireBot tray icon stays in an "Initializing" state indefinitely. The tray menu's "Open Workbook" item reports `"Open Workbook clicked but no spreadsheet configured yet"` even though `config.json` is fully populated with the workbook ID, OAuth email, and EQ folder.

User-visible effect: the install appears to hang. No browser-OAuth re-prompt, no error, no tray-red transition. Just stuck.

## Reproduction

1. Fresh install of SquireBot v0.2.0 on a Windows machine with no prior config (`%LOCALAPPDATA%\SquireBot\config.json` absent + no `SquireBot:*` wincred entry).
2. Launch SquireBot. Wizard fires (browser opens to Google OAuth).
3. Sign in to Google + grant Drive access.
4. Pick a workbook from the Drive Picker.
5. Confirm the auto-detected EQ folder.
6. **Expected:** wizard window closes, tray transitions to "Watching" state, scaffold runs against the picked workbook (creates 9 dimension tabs + initial `_meta` rows), watcher begins monitoring the EQ folder.
7. **Actual:** wizard appears to complete (per logs — see Evidence below), but the tray stays in "Initializing" and the watcher never runs the scaffold.

## Workaround

Quit SquireBot from the tray (right-click → Quit), then relaunch from the Start menu. On the new launch, SquireBot reads `config.json` from disk on startup, sees the populated values, skips the wizard, and runs the scaffold + watcher normally. Catch-up upload fires for any inventory/spellbook files already in the EQ folder.

Time cost of workaround: ~10 seconds + ~5–60 seconds for scaffold to complete.

Note the gap between 23:25:37 (wizard eq-folder confirmed) and 23:27:46 (user clicked Open Workbook): **2 minutes 9 seconds with zero log activity**. No "watcher started", no "scaffold schema v1", no "config saved" — nothing.

Verified `config.json` was correctly persisted by the wizard. After workaround restart at 23:43:51:
- Auto-update check fired
- Watcher started normally
- Catch-up upload completed for 7 characters in 7 seconds

So the data persistence works; only the in-process notification to the watcher goroutine is broken.

## Suspected root cause

The wizard module (`internal/wizard/server.go`) successfully writes `config.json` to disk after each step (verified via inspection: workbook ID, EQ folder, and email all present). But it doesn't signal the running watcher goroutine to reload config or transition out of "wait for setup" mode.

Likely culprits:
1. **Missing channel send.** The main app (`cmd/squirebot/main.go`) probably listens on a channel for "wizard complete" — if the wizard module forgets to send (or the channel was set up wrong), the watcher never gets the signal.
2. **Race condition in startup ordering.** If `runWatcher` checks config state ONCE at startup (when config was empty, so it goes into "wait for wizard" mode) and never re-checks after the wizard completes, that'd produce this exact behavior.
3. **Incorrect state machine in `internal/app/runapp.go`.** A "ready to scaffold" state might depend on a flag that the wizard module doesn't set.

The fix is likely in one of:
- `cmd/squirebot/main.go` — wire the wizard's completion callback to trigger watcher startup
- `internal/wizard/server.go` — emit the signal that triggers watcher startup
- `internal/app/runapp.go` — make `runWatcher` re-check config periodically or on a notification channel

A correct fix should be testable end-to-end by:
1. Wiping `config.json` and the `SquireBot:*` wincred entry
2. Launching SquireBot fresh
3. Completing the wizard
4. Confirming within ~30 seconds that the watcher has scaffolded the workbook + begun monitoring (without restart)

## Fix plan

Cut a v0.2.1 patch release containing the fix.

Steps:
1. Reproduce on dev box (clear state, run wizard, observe stall).
2. Trace the wizard→watcher handoff code path. Likely files: `cmd/squirebot/main.go`, `internal/wizard/server.go`, `internal/app/runapp.go`. Identify the missing signal/notification.
3. Add the missing wiring + a unit test that asserts the watcher transitions to scaffold-ready within N seconds of wizard completion.
4. Test fresh install end-to-end (quit + wipe config + wincred + relaunch + walk through wizard → confirm scaffold runs without manual restart).
5. Tag v0.2.1, push, ship.
6. Update README to remove the workaround callout once v0.2.1 is on `releases/latest`.

## Distribution implications

**Do NOT mass-distribute v0.2.0 to the guild until either:**
- (a) v0.2.1 ships with the fix landed, OR
- (b) the README workaround is in place AND the guild lead is OK telling guildies "if you see Initializing for more than 30 seconds, quit + relaunch."

Pre-v0.2.1, every guildie hits this on first install. The workaround is trivial but undermines the "click installer, walk through wizard, done" UX promise.
