# Phase 19 — UI Design Contract

> Visual and interaction contract for the personal Wantlist CRUD page (WANT-01, WANT-02). Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **This is NOT greenfield.** SquireBot ships a live SvelteKit site (squirebot.quest) with a fully established, approved design system (14-UI-SPEC) extended by login-gated personal-CRUD forms (15-UI-SPEC § Form Contracts + ConfirmDialog) and the `/account` list+remove twin (17-UI-SPEC). **Every spacing / typography / color decision below is INHERITED from that system — nothing here invents a new palette, font scale, or component vocabulary.** This spec's job is to lock how the new `/wantlist` page *reuses and extends* what exists, and to nail the four wantlist-specific interaction contracts: catalog-first add-item search, custom-want flagging, the deep "where + who holds it" in-guild display, and remove.
>
> **shadcn gate: N/A.** shadcn is React-centric; this is SvelteKit. The design system already exists (no `components.json`; tokens live in `web/src/app.css` + `web/src/lib/theme/themes.ts`). No initialization, no registry.
>
> **Phase scope:** pure website CRUD behind the existing Discord-login gate (the AuthGate layout). NO Discord bot, NO DM, NO monitors (Phases 20–23). Add / view / remove a personal, private wantlist + the already-in-guild indicator.

## Wantlist Grid Contract (WANT-02) — the 5th DataGrid instantiation

Reuse `DataGrid.svelte` unchanged; add a `wantlistColumns: ColumnDef<WantlistRow, unknown>[]` to `columns.ts`. **Owner-scoped, consolidated, single grid — never per-character, never per-anything.** The leading column is NOT `Char` here (this is the owner's own list, not a cross-character roll-up) — it leads with **Priority** (the default sort key), and there is no sticky-Char column (set `defaultSorting` to the priority+in-guild seed, not Char). Keep the sticky header row.

**Columns (in order):**

| Column | Source | Cell | Filter | Sort |
|--------|--------|------|--------|------|
| **Priority** | `priority` (`low`/`med`/`high`) | Text badge (High / Med / Low) at Label type — High in `--accent`, Med in `--text`, Low muted `--text@0.7`. Color is not the only signal (the word is present). | facet | **default sort key (high→low)** via a custom `sortingFn` mapping high=3/med=2/low=1 (mirrors `tierSort`) |
| **Item** | `item_name` (+ `item_id`) | Catalog want → accent link + `ItemTooltip` trigger + a de-emphasized `#<item_id>`. Custom want → plain `--text` label + the **custom flag chip** (see below); NO tooltip, NO link. | text | item asc |
| **Reason** | `reason` (`buy`/`quest`) | Text chip "Buy" / "Quest" at Label type, neutral (`--text` over a faint tint) — distinct glyph-free chips so the buy/quest distinction is legible at a glance. | facet | reason asc |
| **In guild?** | computed join (D-06) | The **deep** holder display — see § In-Guild Display. | facet (the coarse In/Not/—) | **secondary sort key** (after priority): in-guild status, so "wanted + no one has it" floats up |
| **Note** | `note` (≤280 chars, optional) | Body text, truncated with an ellipsis past ~1 line; full text on hover/`title`. Blank → empty cell. Renders via plain `{}` (auto-escaped) — never `{@html}`. | text | (unsorted) |
| **Remove** | — | The per-row destructive control — see § Remove Interaction. | none | none |

**Default sort (D-08):** `priority` (high→low) **then** `in_guild` status. Seed via the DataGrid `defaultSorting` prop with `enableMultiSort` (already on): `[{ id: 'priority', desc: true }, { id: 'in_guild', desc: false }]`.

**The buy+quest duplicate (D-05):** the same item may legitimately appear as two rows (one Buy, one Quest). They are NOT an accidental duplicate and must not look like one. The **Reason chip is load-bearing** as the visual differentiator — the two rows are visibly distinguished by their Reason cell, and (since the default sort groups by priority then in-guild, not by item) they may not even be adjacent. Do not add a "duplicate" warning; do not de-dupe in the view. (The handler rejects only an *exact* same-item-same-reason duplicate — the user-visible rule.)

**Grid behavior (inherited from DataGrid):** sortable headers (click / Enter / Space, accent caret); a global filter + per-column facet/text filters; client-side (data is tiny — one guildie's wants); no pagination, fixed-height scroll region under the sticky header; zebra + hover at ~4–8% accent alpha. The `no-rows` "No rows match the current filters" message is the *filtered-to-empty* state; the *genuinely-empty* wantlist uses the `no-wants` StateBlock above the grid instead (the grid is not rendered when there are zero wants).

## In-Guild Display Contract (WANT-02 / D-06, D-07) — the core-value surface

This is the phase's signature interaction and it goes **deep**, not a bare yes/no checkmark. It directly delivers the project core value ("what do I need, and WHERE in the guild is it"). It joins the wantlist row's stable `item_id` against the existing **consolidated all-character inventory** (`compute.Bank` / the `view` data — worn + carried + bank, ALL locations, per locked D-06 "not bank-toon-only") — a join, not a rebuild.

> **Wording reconciliation (review MUST-FIX 3):** the join is all-inventory, not bank-toon-only, so the indicator is labelled **"In guild" / "Not in guild"** — NOT "In bank". An item only *worn* by a guildie and never banked is still "In guild" and the badge says so honestly. ROADMAP success-criterion #3 ("already in the guild bank?") is SATISFIED by this broader indicator: anything in the bank is in the guild, so "in guild" is a superset of "in the bank" (it never *under*-reports the bank). D-06 deliberately chose the deeper all-guild display.

**Three states, rendered in the In-guild? cell:**

1. **Held (catalog want, ≥1 holder):** a `--status-ok` "In guild" badge (StatusCell pattern, word present) **followed by one line per holding character**, reusing the **exact** `SearchResults` holder framing already shipped:
   `↳ <Char>: <count>` (e.g. `↳ Borticus: 2`, `↳ Slampeach: 1`), Body type, tabular-nums, `--text`. Reuse `SearchResults.svelte`'s VISUAL ↳-line styling so the two surfaces read as one language — but NOT its data shape: SearchResults is location-granular (`↳ <Char>: <location>, count <n>`, one line per location) and `ViewRow` has no `location` field, so the wantlist line is the (char + summed-count) shape below.
   - **Per-character summing (review MUST-FIX 1 — load-bearing):** the `view` payload is RAW `inventory_item` rows (one row per location/stack, NO GROUP BY — `InventoryJoin`), so a character commonly holds the same `item_id` in several rows (worn + bank, or multiple stacks). Each character must appear **exactly once** with its counts **SUMMED** — `↳ Borticus: 2`, never two `↳ Borticus: 1` lines. The grouping happens client-side in `holdersFor` (§ holders.ts) BEFORE rendering.
   - **Collapse rule (inherited):** if >5 holders (distinct characters), show the first 5 + a "Show all N holders" / "Show fewer" accent text toggle — the same `COLLAPSE_THRESHOLD = 5` + expand affordance `SearchResults` already implements. (A wantlist will rarely have >5 holders for one item, but reuse the existing rule rather than inventing a cap.)
   - The badge word ("In guild") carries the meaning so the green is never the only signal.

2. **Not held (catalog want, 0 holders):** a `--status-missing` "Not in guild" badge (word present). No holder lines. This is the high-value row — combined with the default sort (priority then in-guild), the wanted-and-nobody-has-it items surface near the top.

3. **N/A (custom want, `item_id` NULL — D-07):** a muted **"—"** (em-dash) in `--status-other`/muted `--text`, with the custom flag chip carrying the "won't trigger alerts" explanation. Custom wants are excluded from the join entirely (no lookup) — the cell is never green/red, only the neutral dash.

**Why the holder lines and not a count badge:** the CONTEXT specifics call this out explicitly — "not just a checkmark, but 'Borticus has 1, guild bank has 2.'" The holder lines ARE that. They reuse the shipped `SearchResults` treatment so there is zero new visual vocabulary.

## Add-Item Contract (WANT-01 / D-03, D-04) — catalog-first + custom escape hatch

The add affordance is a small block at the top of the `.form-card` (above the grid). It is a **catalog-first search** that resolves to a pinned `item_id`, with a deliberate **custom text want** escape hatch. Reuse the existing `searchIndex.ts` fuzzy engine + the "did you mean?" pattern; the difference from the read-only `SearchBox` is the *corpus* (the item catalog, by name+ID) and the *outcome* (it stages a want, it doesn't just display holdings).

**Flow:**
1. A single search field (`Search items to add…` placeholder + the Lucide search icon), styled exactly like the shipped `SearchBox` `.search-field` (44px target, accent focus-within ring, max-width ~480px).
2. As the guildie types, show catalog matches (name + de-emphasized `#<item_id>`, each an `ItemTooltip` trigger so they can confirm it's the right item before adding). Match is the ported case-insensitive substring + group-by-item engine.
3. **"Did you mean?" (D-03):** on **no exact catalog match**, show the single clickable inline best-fuzzy suggestion — the SAME `Did you mean <suggestion>?` accent-link pattern from `SearchResults` (re-runs the search with that term). Carry forward the 999.28 empty-query guard (already fixed in the shipped engine).
4. Picking a catalog result pins its `item_id` and reveals the **want detail fields** (below) with the Item locked to that catalog entry.
5. **Custom text want (D-04):** if the catalog has no match, an explicit affordance — `Add "<query>" as a custom want` (an accent text button) — stages a want with `item_id` NULL and the typed text as the label. It MUST surface the custom consequence inline before commit (see custom flag).

**Want detail fields (FormField rhythm, reuse `FormField.svelte`):**

| Field | Control | Required? | Default | Notes |
|-------|---------|-----------|---------|-------|
| Item | (locked from the catalog pick, or the custom text) | — | — | Read-back display, not editable here |
| **Reason** | native `<select>` (Buy / Quest) | **required** (D-01) | none — must choose | Styled like the `CharMetaForm` `.field` select (44px, `--panel`, accent focus). No blank-success: the Add button is disabled until a reason is chosen. |
| Priority | native `<select>` (Low / Med / High) | optional | **Med** (D-01) | Pre-selected to Med. |
| Note | `<textarea>` | optional | empty | `maxlength=280` (D-01); show a live "N/280" counter at Label type, muted; counter goes `--status-missing` only at the cap. Renders back via plain `{}`. A whitespace-only note is treated as empty (the server trims before the 280-rune check + stores NULL). |

**Primary CTA:** the established accent primary button (accent fill, `--bg` text, 13px/600 display uppercase, 44px, the `WatcherCodesPanel`/`CharMetaForm` `.primary` treatment) — label **"Add to wantlist"**. Disabled until: an item is chosen (catalog pick OR custom text non-blank) AND a reason is selected. A `LoaderCircle` spin + "Adding…" during the request (mirror `CharMetaForm`'s save spinner).

**Custom-want flag (D-04 — mandatory, both at add-time and in the row):**
- A neutral (`--status-other`, NOT red) Label-type chip reading **"Custom — won't trigger alerts"** appears (a) inline in the add block once the custom path is chosen, and (b) in every custom row's Item cell.
- The intent (CONTEXT specifics): a guildie must not be surprised later when Phases 21+ never DM them about a custom want. The chip is the contract. Tooltip/title on the chip: `Custom wants aren't matched against the item catalog, so the EC/WTS/raid monitors can't alert you about them.`

## Remove Interaction (WANT-02) — the destructive twin of `/account` Revoke

Per-row Remove is the **only destructive action** this phase. It reuses the shipped destructive pattern exactly (15-UI-SPEC + the `/account` `WatcherCodesPanel` Revoke).

- **Resting control:** a quiet destructive-text ghost button in the Remove column — `--destructive` text + 1px `--destructive` outline, transparent fill, Label type, 44px (the SAME `.revoke-btn` treatment from `WatcherCodesPanel`). A Lucide `trash-2` glyph + "Remove" (icon carries meaning alongside color). The full destructive *fill* is reserved for the ConfirmDialog confirm — never the resting row button.
- **Confirm-before-commit:** clicking opens the shared `ConfirmDialog.svelte` (focus → Cancel, Esc/backdrop/Cancel dismiss with no side effect, focus-trap, focus restored). The destructive confirm carries the triangle-alert glyph + an explicit confirm label (Heavy's dark-destructive contrast caveat is already handled in `ConfirmDialog`).
- **Optimistic-collapse + reload:** on confirm, re-fetch the owner's wantlist from the server (mirror `WatcherCodesPanel.doRevoke`'s server-truth reload) so the grid stays authoritative; surface a polite `aria-live` success line.
- **Server-truth (D-09):** the owner is derived server-side from the Discord session; the remove call sends the want's id only, never an owner. A 401 bubbles to AuthGate → LoginScreen via the existing `authGuard`. IDOR-safe + audited (the `account.go` / `audit.go` seam).

## Accessibility & Interaction Notes (inherited obligations)

- **Keyboard:** grid headers sortable via Enter/Space; the add-search, reason/priority selects, note textarea, "did you mean?" link, Add, and Remove all Tab-reachable; the ItemTooltip opens on focus and closes on Esc; ConfirmDialog traps focus and restores it. Visible focus ring in `--accent`.
- **Touch:** 44px min targets on every control; tooltips open on tap, dismiss on outside-tap.
- **Reduced motion:** honor `prefers-reduced-motion` (the global `app.css` rule + the existing component animations already comply — the add spinner and dialog fade go instant).
- **Color is never the only signal:** the In-guild "In guild" / "Not in guild" / "—" words, the Reason and Priority badge words, and the custom-want chip text all back their color encodings.
- **XSS trust boundary (inherited, load-bearing):** item names, custom labels, and notes are user/wiki-controlled. They render ONLY via plain `{}` (Svelte auto-escapes) — NEVER the raw-HTML directive. The single sanctioned `{@html}` sink remains `ItemTooltip` → `composeItemNote` (which escapes every interpolated value). A custom want label and a note must be inert text.
- **noindex (inherited):** the site is `noindex`; this login-gated page inherits it.
