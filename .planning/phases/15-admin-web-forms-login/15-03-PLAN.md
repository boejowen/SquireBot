SQLite write-transaction note: modernc.org/sqlite honors `BEGIN IMMEDIATE` to take the write lock up front. Use `tx, _ := db.BeginTx(ctx, nil)` then `tx.ExecContext(ctx, "BEGIN IMMEDIATE")` is NOT how database/sql works — instead open the tx and ensure the FIRST statement is a write OR run the officer re-check SELECT + the writes in the same tx so they're atomic. For an explicit immediate lock with database/sql + modernc, use a DSN/conn with `_txlock=immediate` OR execute the guard SELECT + mutation in one tx (the re-check-inside-tx is what closes TOCTOU; the IMMEDIATE keyword is the belt-and-suspenders). Document whichever you choose in a comment containing the literal string "BEGIN IMMEDIATE" so the acceptance grep + the security intent are visible.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated browser → write endpoints | destructive (eviction, officer-removal) + mutating (coin, officer-add) requests cross here — this phase's first destructive surface |
| session identity → authorization decision | the acting discord_user_id (from the session) drives officer/owner-floor checks |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-15-13 | Elevation of privilege | officer/eviction endpoints (TOCTOU) | mitigate | Re-check IsOfficer INSIDE the write transaction (BEGIN IMMEDIATE write-lock posture); a just-removed officer cannot get one final write through (v1 WR-04 close); RequireOfficer middleware is the outer gate, the in-tx re-check is the authoritative one |
| T-15-14 | Elevation of privilege | officer-removal of the maintainer | mitigate | Owner-floor protection: RemoveOfficerTx + the eviction owner-floor check reject a peer targeting the floor (403 owner_floor_protected) before any write |
| T-15-15 | Tampering | malformed coin input | mitigate | Server-side range validation (plat>=0, gold/silver/copper 0–999) → 400 invalid_input; SetCoinTx rejects non-bank-toon (not_bank_toon) — never trust the client's disabled-button UX |
| T-15-16 | CSRF | state-changing POST forms | accept (documented posture) | Per 15-RESEARCH/CONTEXT D-05 the chosen posture for ASVS L1 here is SameSite=Lax cookie + credentialed EXACT-ORIGIN CORS + JSON Content-Type. SameSite=Lax blocks cross-site form-POST cookie attachment; the exact-origin CORS (no `*`) blocks cross-origin fetch; JSON body + no simple-form content-type means a cross-site `<form>` can't forge it. This is sufficient for ASVS L1 for this low-sensitivity hobby app — documented explicitly so it reads as a decision, not an omission. (A CSRF token can be added later if the guild's risk posture changes.) |
| T-15-17 | Repudiation | who evicted / promoted / set coin | mitigate | Every write appends an append-only audit_log row (event + actor=acting discord id + detail JSON); audit_log has no UPDATE/DELETE path in app code |
| T-15-18 | Denial of service | concurrent destructive writes racing | mitigate | The write-lock posture (BEGIN IMMEDIATE / single-writer WAL, SetMaxOpenConns(1)) serializes writers; a contended write surfaces as lock_busy to the client (UI-SPEC "Another officer action is in flight. Please retry.") rather than corrupting state |
</threat_model>
