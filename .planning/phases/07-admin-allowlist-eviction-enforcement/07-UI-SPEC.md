## Context Notes (read first)

There is no Tailwind, no shadcn, no Radix, no Next.js — this is Apps Script V8 runtime serving an inline `<style>` block over a 300px HtmlService panel. The standard GSD "shadcn gate" does NOT apply (the environment is Google Apps Script HtmlService, not a JS framework). The "tool = none, preset = not applicable" cells below are correct, not gaps.

## Color

The admin-mgmt sidebar consumes the same six theme palettes through the same CSS custom properties as every other v1.0 sidebar. No new colors introduced. Below is the **token map** (the role each variable plays in this sidebar); concrete hex values vary by active theme and are documented in `apps-script/src/lib/themes.ts:35-67`.

| Role | Token | Source token in `Theme` | Sidebar usage |
|------|-------|-------------------------|---------------|
| Dominant (60%) — sidebar background | `--bg-row` | `theme.rowAltBg` | `<body>` background, input/select background |
| Secondary (30%) — header strip / border accent | `--bg` | `theme.headerBg` | Input/select border (the only place this token surfaces in the eviction sidebar; admin-mgmt mirrors this) |
| Foreground text | `--fg` | `theme.rowFg` | Body text, list rows, input text |
| Heading color | `--fg-header` | `theme.headerFg` | `h3` "Manage admins" |
| Accent (10%) — primary button | `--accent-bg` / `--accent-fg` | `theme.accentBg` / `theme.accentFg` | `button.primary` ("Add admin") background + text. Also: `:focus` outline on the email `<input>`. |

**Accent reserved for** (explicit, exclusive list):

1. The single `Add admin` primary button background + foreground.
2. The `:focus` outline ring on the email text input.
3. The `(owner)` annotation badge color (optional polish; if implemented, it uses `--accent-bg` text color at 11px on the floor row).

**NOT accent-colored:** the per-row "Remove" buttons (these use the muted destructive treatment below), the section headings, the status region, the description text.

| Role | Token | Sidebar usage |
|------|-------|---------------|
| Destructive | hard-coded `#c00` (from eviction sidebar `#msg.error` line 244) | Error-state status text only (e.g. "Owner-floor protected"). NOT used for the Remove button. |
| Success | hard-coded `#060` (from eviction sidebar `#msg.success` line 245) | Success-state status text ("Admin added", "Admin removed"). |

**Remove button styling (intentional contract diff from eviction):**

The eviction sidebar has a single big primary "Evict" button; the admin-mgmt sidebar has many small per-row "Remove" buttons. These buttons must be visually subordinate to the primary "Add admin" button to keep the visual hierarchy clear (Add is the constructive action; Remove is a maintenance action). Treatment:

| Property | Value | Rationale |
|----------|-------|-----------|
| Background | `transparent` | Visually subordinate; doesn't compete with the primary Add button |
| Color | `var(--fg)` at `opacity: 0.7` | Muted; not destructive-red (red would suggest danger that doesn't match the reality — removal is reversible via re-add) |
| Border | `1px solid var(--bg)` (i.e. theme `headerBg`) | Outlines the button so it remains tappable-looking against the row background |
| Font-size | 11px | One step down from body — matches `.desc` / `.grace` scale |
| Padding | `4px 8px` (xs / sm) | Tight; per-row context |
| Border-radius | 3px | Matches `select`/`button.primary` from eviction sidebar |
| Min-height | 24px | Below the 32px primary minimum because these are secondary controls; still keyboard-/touch-reachable |
| Hover state | `opacity: 1` + `border-color: var(--accent-bg)` | Standard cue; no color change |
| Disabled / suppressed | not rendered at all on the owner-floor row when caller != floor | Per D-04 client-side enforcement |

**Why not destructive-red on Remove?** Removal is a reversible allowlist edit (admin can be re-added in 5 seconds). Treating it visually equivalent to the eviction sidebar's destructive flow would over-cue danger and create a "boy who cried wolf" effect on the real destructive surface (eviction). Reserved-for-eviction destructive palette stays untouched.

## Interaction Contract

### Flow 1 — Open "Manage Admins…" as an admin

1. User clicks `SquireBot → Manage Admins…` in the menu.
2. `showAdminMgmtSidebar()` runs. First statement (D-03 / D-05 boundary):
   ```typescript
   const callerEmail = (Session.getEffectiveUser().getEmail() ?? '').toLowerCase().trim();
   if (!isAdmin(callerEmail)) {
     SpreadsheetApp.getUi().alert('Not authorized',
       'Only guild officers can manage admins. Contact a workbook admin if you think this is wrong.',
       SpreadsheetApp.getUi().ButtonSet.OK);
     return;
   }
   ```
3. Admin caller → sidebar opens at 300px, theme-injected. Calls `getAdminList()` immediately (no `init()` flicker — same pattern as eviction sidebar line 261).
4. `getAdminList()` returns `{ admins: string[], floor: string, callerEmail: string }`. Client-side renders:
   - List header `Current admins (N):` with `N` = `admins.length`.
   - One `<li>` per admin (sorted, already-lowercased server-side per D-02).
   - For each row, append ` (owner)` if `admin === floor`, with the `title=` tooltip set.
   - Render `[Remove]` button on every row EXCEPT the floor row when `callerEmail !== floor` (client-side D-04 enforcement; the server enforces it again on `removeAdmin`).
5. The Add admin input gets focus on mount (`document.getElementById('addInput').focus()` at the end of the success handler).

### Flow 2 — Open "Manage Admins…" as a non-admin

1. User clicks `SquireBot → Manage Admins…`.
2. `showAdminMgmtSidebar()` admin-check fails.
3. Modal `getUi().alert('Not authorized', '...manage admins...', ButtonSet.OK)` appears (D-03).
4. User clicks OK; modal dismisses; no sidebar opens; no state changes anywhere.

### Flow 3 — Add admin

1. Admin types `newadmin@example.com` into the input.
2. Admin clicks `Add admin` (or presses `Enter` while focused in the input — keyboard shortcut, see §A11y below).
3. Add button disables (loading state).
4. `google.script.run.addAdmin(emailValue)` fires. Server-side: `requireAdminOrThrow` → lock → trim+lowercase → reject if empty or missing `@` → idempotent check → append to JSON array → append audit log entry → release lock.
5. Server returns `{ added: true }` or `{ added: false, alreadyExists: true }`.
6. Client-side success handler: clears the input, re-fetches `getAdminList()`, re-renders the list, writes the status message per the table in §Copywriting → Status region.
7. Add button re-enables.

### Flow 4 — Remove admin (non-floor target)

1. Admin clicks `[Remove]` on a non-floor row.
2. `window.confirm(body)` fires with the verbatim copy from §Per-row Remove confirmation.
3. User clicks OK.
4. `google.script.run.removeAdmin(targetEmail)` fires. Server: admin-check → lock → trim+lowercase → owner-floor check (passes, target ≠ floor) → splice out → append audit log → release.
5. Client-side: re-fetch + re-render list. Status message: `Admin removed: {email}.`

### Flow 5 — Remove attempt against floor by non-floor caller

1. Per D-04 client-side enforcement, the Remove button is **not rendered** on the floor row when `callerEmail !== floor`. So the typical case never gets here.
2. **Defense-in-depth case:** if a stale sidebar (caller was just demoted) tries to invoke `removeAdmin(floor)`, the server-side `removeAdmin` reads `_meta.workbook_owner_floor`, checks `target === floor && caller !== floor`, throws `Error('owner_floor_protected')`.
3. Client-side failure handler: status message `Owner-floor protected — only the workbook owner can remove themselves. No changes were written.`

### Flow 6 — Self-removal by the owner-floor

1. Floor user clicks `[Remove]` on their own row (button IS rendered, because `callerEmail === floor`).
2. Standard confirm dialog.
3. `removeAdmin(floor)` succeeds server-side (D-04 explicitly allows self-removal of floor).
4. Sidebar list re-renders without the now-removed email. The `_meta.workbook_owner_floor` row is NOT updated (orphan pointer; documented as intentional per D-04).
5. Status: `Admin removed: {email}.`

### Flow 7 — First-run bootstrap (manual fallback path)

1. Owner clicks `SquireBot → Initialize Admin Allowlist (manual)` (under "Admin (Phase 7)" sub-section).
2. `bootstrapGuildAdminsManual()` fires `getUi().alert(...)` with the verbatim copy from §Bootstrap confirmation modal, ButtonSet `OK_CANCEL`.
3. OK → `bootstrapGuildAdmins({ seedEmail, initiatedBy: 'manual_fallback' })` runs. Lock-wrapped. Idempotent check: if `_meta.guild_admins` is already a non-empty array, returns `{ bootstrapped: false }` (and the toast says `Admin allowlist already initialized.`).
4. Success path: writes `_meta.guild_admins`, `_meta.workbook_owner_floor`, appends `_meta.admin_log` bootstrap entry. Toast `Admin allowlist initialized with {email}.` via `SpreadsheetApp.getActiveSpreadsheet().toast(...)`.

### Flow 8 — Audit-log envelope (mentioned, not displayed)

Every `addAdmin` / `removeAdmin` / `bootstrapGuildAdmins` writes one entry to `_meta.admin_log`. The envelope is documented for completeness — it is **NOT surfaced in this sidebar's UI** (no log viewer in Phase 7; consumers inspect the `_meta` tab directly).

```typescript
{ at: ISO8601, action: 'add'|'remove'|'bootstrap'|'bootstrap_failed', email: string, initiated_by: string }
```

The `initiated_by` field falls back to `'unknown'` when `Session.getEffectiveUser().getEmail()` returns empty (D-06 audit-log soft fallback). Authorization checks use the empty string as fail-closed (D-06).
