## Task 1 — Surface cross-owner ingest rejection on the tray (item #1)

**Problem:** `internal/app/runapp.go` `handleIngestErr` handles a 409 cross-owner reject with
only `slog.Warn` + `return true`. Unlike the `ErrUnauthorized` (401) branch just above it, it
does NOT touch the tray — so the icon stays green/"Connected" and the user sees a permanent
silent failure (exactly what made Kim's issue invisible).

**Files:** `internal/app/runapp.go`

**Action:** In the `case errors.Is(err, backend.ErrCrossOwner):` branch (~line 360), after the
existing `slog.Warn("cross-owner reject", ...)`, add tray surfacing that mirrors the
`ErrUnauthorized` branch's pattern (`t.SetIconHealth(tray.HealthRed)` + a clear `t.SetStatus`).
Use the `charName` and `traySuffix` already in scope. Suggested status text (finalize wording
to match the file's voice):

```go
case errors.Is(err, backend.ErrCrossOwner):
    slog.Warn("cross-owner reject", "char", charName)
    t.SetIconHealth(tray.HealthRed)
    t.SetStatus("Rejected: " + charName + traySuffix + " is registered to another guildie")
    return true // terminal; NO retry (unchanged)
```

Keep `return true` (terminal, no-retry) — that behavior is unchanged and already tested.

**Note (scope):** the report also mused about systemd-journal visibility on Linux. That is a
logging-sink change (the Linux watcher logs to a lumberjack file, not the journal) and is OUT OF
SCOPE here — the tray surfacing is the targeted fix and matches the existing 401 pattern. If you
want, note the journal idea as a deferred follow-up in the SUMMARY; do not implement it.

**Verify:**

- `go test ./internal/app/...` — existing `TestMakeOnSpellbookChange_409CrossOwnerNoPersist`
  still passes (it asserts one-request + no-mtime-persist; it does NOT assert tray state, so it
  is unaffected).
- Add a tray-state assertion ONLY if `tray.Controller` already exposes a way to read the

**Done:** cross-owner 409 turns the tray red with an informative status; build + app tests green.

## Task 2 — `--reconfigure` flag to force re-onboarding (item #2)

**Problem:** `squirebot --setup` (`app.RunSetup`) is a no-op once a guild code AND an EQ folder
are configured — it prints "setup complete" and exits without re-prompting, so a user cannot
re-point the folder or re-enter a code without manually moving `config.json` aside.

**Files:** `internal/app/runapp.go` (`RunSetup`), `cmd/squirebot/main.go` (dispatch).

**Action:**

1. `RunSetup` — add a trailing `force bool` parameter. When `force` is true, always re-run
   onboarding (re-prompt + validate + store the code) AND re-pick the EQ folder, regardless of
   existing config:

   ```go
   func RunSetup(ctx context.Context, cfg *config.Config, baseURL, version string, t *tray.Controller, force bool) error {
       code, err := credstore.Read()
       if force || err != nil || code == "" {
           if _, oErr := runOnboarding(ctx, cfg, baseURL, version, t); oErr != nil {
               return oErr
           }
           // A forced reconfigure also re-points the EQ folder — runOnboarding only
           // prompts for it when none is configured, so do it explicitly here.
           if force {
               return pickAndSaveEQFolder(ctx, cfg, t)
           }
           return nil
       }
       if !hasEQFolder(cfg) {
           return pickAndSaveEQFolder(ctx, cfg, t)
       }
       return nil
   }
   ```
   Update the `RunSetup` doc comment to document the new `force` behavior. (D-07 is about
   `RunApp` staying byte-unchanged — `RunSetup` is the separate function precisely so it CAN
   change; this is fine.)

2. `cmd/squirebot/main.go` — the only caller (line ~197). Accept `--reconfigure` as a sibling of
   `--setup` and pass `force`:

   ```go
   if len(os.Args) >= 2 && (os.Args[1] == "--setup" || os.Args[1] == "--reconfigure") {
       force := os.Args[1] == "--reconfigure"
       ...
       // Skip EQ-folder auto-discovery on a forced reconfigure so the user re-points explicitly.
       if !force && !hasAnyEQFolder(cfg) {
           ...existing eqfind.Discover() block...
       }
       if err := app.RunSetup(setupCtx, cfg, baseURL, Version, setupTray, force); err != nil {
           ...
       }
       fmt.Fprintln(os.Stderr, force ? ... : "SquireBot setup complete.") // Go has no ternary — use an if/else to pick the message
       os.Exit(0)
   }
   ```
   (Go has no ternary — pick the completion message with a small `if force { ... } else { ... }`.)
   Update the `--setup` lead comment to mention `--reconfigure`. Keep this Linux-path scoped, as
   the existing comment notes (Windows onboarding stays tray/wizard-driven).

**Verify:**
- `go build ./...` clean (confirms the single caller + signature line up).
- `go test ./internal/app/... ./cmd/squirebot/...` green.
- Add a `RunSetup(force=true)` unit test ONLY if it can be done on the dev platform without new
  shims. Note: `onboarding.PromptGuildCode`/`PickEQFolder` have an injectable `stdin` seam on the
  `!windows` build (`internal/onboarding/dialog_other.go`), but the Windows dev box compiles the
  Win32 dialog (`dialog_windows.go`), which can't run headless. If a clean cross-platform seam to
  drive the prompts in a test isn't already present, document the gap in the SUMMARY and rely on
  `go build` + the existing onboarding tests rather than building new test infrastructure.

**Done:** `squirebot --reconfigure` forces a full re-onboard (code + folder) even when already
configured; plain `--setup` behavior is unchanged; build + app/cmd tests green.

**Commit:** `feat(watcher): add --reconfigure to force re-onboarding when already set up`
