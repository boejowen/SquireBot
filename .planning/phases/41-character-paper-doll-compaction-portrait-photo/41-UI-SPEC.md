# Phase 41 — UI Design Contract

> Visual and interaction contract for the Characters-tab paper-doll compaction (CHARUI-01) and the optional per-character portrait photo (CHARUI-02). Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Every value below is derived from the LOCKED `41-CONTEXT.md` decisions (D-01..D-08) and the existing EQ-aesthetic design system** (`docs/design/eq-aesthetic-theme.md` → `web/src/lib/theme/themes.ts` + `web/src/app.css`). ### CHARUI-01 compaction — concrete target values (D-01)

The compaction TIGHTENS the existing grid; it does NOT restructure it. Keep the 3-column `equip-col / doll / equip-col` `.paperdoll` grid and the 62px tile module.

| Property | Current (`InventoryWindow.svelte`) | Phase-41 target | Rationale |
|----------|-----------------------------------|-----------------|-----------|
| `.paperdoll` grid `gap` | `24px` (lg) | **`16px` (md)** | Reclaim the loose center gap; still on-scale, still reads as three columns |
| `.paperdoll` `@media (max-width:640px)` `gap` | `16px` | **`8px` (sm)** | Tighter on mobile where horizontal room is scarce |
| `.doll` `min-height` | `260px` | **REMOVE the fixed 260px min-height** — the frame is sized by its own `aspect-ratio`, not a floor | The 260px floor is the dead space CHARUI-01 exists to reclaim |
| Portrait frame footprint | ~oversized dashed box | **square frame, width `= 3 tiles + 2 gaps = 190px` → `min(190px, 100%)`, `aspect-ratio: 1 / 1`** | `3 × 62px + 2 × 8px = 202px`; snap to **190px** so the figure column reads slightly narrower than the two 2-tile equip columns and the whole paperdoll tightens. Square = portrait-photo-friendly and matches D-04's square client downscale |
| Frame `border-radius` | `4px` | `4px` (unchanged) | Consistent with `.doll` / `.bag-expand` radii |
| Frame padding (fallback state) | (n/a) | `8px` (sm) around the silhouette + name | Centers the fallback glyph without reintroducing dead height |

The two `.equip-col` grids, the `.grid` item grids, the `.worn` row, the char-head, and the eyebrows are **unchanged** — the compaction is the `.paperdoll` gap + the `.doll → portrait frame` swap only. Explicitly NOT a full EQ-window teardown (out of scope, `41-CONTEXT.md` domain).

Exceptions: the 44px minimum touch-target height on the upload/remove buttons + the file `<input>` trigger (accessibility floor, already used across the app's controls). Not a spacing-scale value; a hit-area floor.

## Typography

Uses the app's 4-role ramp verbatim (no new sizes). Weight is `var(--weight-display)` for the two display/label roles (600 on four themes, 400 on minimalist — the one sanctioned weight-variance) and normal (400) for body.

| Role | Size | Weight | Line Height | Where in this phase |
|------|------|--------|-------------|---------------------|
| Body | 16px | 400 | 1.5 | Upload help text, the formats/size hint, validation + success messages, the fallback frame name line (`--font-body`) |

| Heading | 20px | `var(--weight-display)` | 1.2 | Not introduced here (the char-head name is Display; no new headings) |

Body line-height 1.5; heading/label line-height 1.2. Fonts are always `var(--font-display)` / `var(--font-body)` — never a literal family (theme-portability requirement).

## Color

The 60/30/10 split is expressed through the theme tokens (values below are the **velious default**; the same token names resolve per theme). Accent is scarce and reserved.

| Role | Token (velious value) | Usage |
|------|-----------------------|-------|
| Dominant (60%) | `--bg` (`#060b18`) | Page background behind the window |
| Secondary (30%) | `--panel` (`#0f1729`) | The portrait frame fill, the upload-control container, the examine/pin panel — every raised surface |
| Accent (10%) | `--accent` (`#a8c5e0`) | The upload primary-button fill, the frame focus ring, the char-head name — RESERVED list below |
| Destructive | `--destructive` → `var(--status-missing)` (`#e88a8a`) | The **Remove portrait** action (D-08) + inline validation error text ONLY |

Accent reserved for (explicit — never "all interactive elements"):
- The **primary upload button** fill (accent background, `--bg` text) — mirrors `CharMetaForm .primary` / `StateBlock .retry`.
- The portrait frame's **hover/focus ring** when it is an interactive editor affordance (`box-shadow: 0 0 0 1px var(--accent)` + `outline: 2px solid var(--accent)`), mirroring the `PaperdollSlot` filled-tile focus treatment.
- The char-head character name (existing `.charname`, unchanged).

Destructive/`--status-missing` reserved for: the **Remove portrait** button styling + confirmation, and inline validation-error copy (wrong type / too large). Success confirmations use `--status-ok` (mirrors `CharMetaForm .result.success`). Neutral surfaces use `--panel`; neutral borders use `var(--border, var(--accent))` exactly as the existing tiles/panels do.

**Portrait frame border:** the FALLBACK (empty) state keeps the existing `1px dashed var(--border, var(--accent))` at `opacity: 0.8` (signals "nothing here yet"). The FILLED state uses a `1px solid var(--border, var(--accent))` (a real, framed photo), matching the tile/panel solid-border idiom. No new color — a dashed→solid switch on the same token.

**No new tokens, no literal hex.** (The one codebase-sanctioned non-token color — the per-item tile hue gradient in `PaperdollSlot` — is NOT used here; the portrait renders a real `<img>` or the silhouette, never a hued gradient.)

Non-text contrast: the frame border, the focus ring, and the destructive text all resolve to tokens already ≥3:1 vs `--panel` per theme (the same tokens the P40 flag rings + the existing focus rings were checked against). No per-theme exception needed — this phase adds no new color pairing.

## Copywriting Contract

Exact strings (copy the executor ships verbatim; `{name}` = the selected character name, rendered via plain `{}` interpolation — Svelte auto-escapes, never `{@html}`).

| Element | Copy |
|---------|------|
| Primary CTA (no portrait yet) | **Add photo** |
| Primary CTA (portrait exists) | **Change photo** |
| Upload in-progress button | **Uploading…** (with the `loader-circle` spinner, mirroring `CharMetaForm` "Saving…") |
| Destructive action | **Remove photo** |
| File-picker trigger label | **Choose an image…** (opens the hidden native `<input type="file">`) |
| Formats / size hint (help text under the control) | **PNG, JPEG, or WebP, up to 256 KB. Square images look best.** |
| Preview confirm button | **Save photo** |
| Preview cancel button | **Cancel** |
| Portrait `<img>` alt text | `{name}` (the character name — meaningful alt, D-07 read view) |
| Fallback frame accessible note | The frame is `aria-hidden` decorative (the `⚔` silhouette + the `{name}` line beneath), exactly as today — the char name is already announced by the char-head `<h1>` |
| Empty state (no portrait, viewer CAN edit) | Heading: **No photo yet** · Body: **Add a photo to give {name} a face on the paper-doll.** |
| Empty state (no portrait, viewer CANNOT edit) | No control, no prompt — the fallback silhouette renders silently (the read view is identical to today for non-editors) |
| Success message | **Saved {name}'s photo.** (`aria-live="polite"`, `--status-ok`) |
| Success after remove | **Removed {name}'s photo.** (`aria-live="polite"`, `--status-ok`) |
| Error — wrong type | **That file isn't a PNG, JPEG, or WebP. Choose an image in one of those formats.** (`--status-missing`) |
| Error — too large | **That image is too large (max 256 KB). Try a smaller or more compressed image.** (`--status-missing`) |
| Error — generic upload failure | **Couldn't save the photo. No changes were made.** (`--status-missing`, mirrors `CharMetaForm` phrasing) |
| Remove confirmation | **Remove photo:** _Remove {name}'s photo? This can't be undone, but you can add a new one anytime._ (a confirm step before the `DELETE`, matching the app's destructive-action posture) |

CTA is a specific verb+noun ("Add photo" / "Change photo" / "Remove photo"), never "Submit" or "OK". Errors state the problem AND the next step. The destructive action carries an explicit confirmation.

## Interaction & State Contract

This is the sixth dimension the checker verifies — the states the portrait frame + upload control move through.

### Read view (all signed-in users — D-07 / D-05)

The portrait frame is the reclaimed `.doll` region. It renders ONE of:

1. **Portrait present** (`has_portrait === true`): an `<img>` sourced from `GET /api/v1/characters/{name}/portrait`, **cache-busted by `?v={portrait_updated_at}`** (D-07). Sizing: fills the square frame, `object-fit: cover`, `border-radius: 3–4px`. `alt={name}`. On `onerror`, **hide the `<img>` and fall through to the silhouette** — the exact `PaperdollSlot.onImgError` hide-and-fall-through pattern (`e.currentTarget.style.display = 'none'`), so a broken/expired blob degrades gracefully to the fallback instead of a broken-image glyph.
2. **Loading** (the `<img>` is fetching): the silhouette fallback shows underneath the `<img>` (the `<img>` paints over it once loaded) — no separate spinner needed; the frame is never empty.
3. **Fallback / no portrait** (`has_portrait === false`): the existing `⚔` silhouette (`--text`, `opacity: 0.5`, 64px) + the dimmed `{name}` line — kept verbatim from today (D-07 "the existing placeholder stays the fallback"). Discretion (`41-CONTEXT.md`): keeping the `⚔` silhouette over a class/race-derived one is the low-risk default; do NOT block on deriving class art.

The read view is byte-for-byte the same for non-editors as today when no portrait is set — the ONLY read-view change is that a set portrait renders in place of the silhouette.

### Editor controls (visible ONLY to an eligible editor — D-05 / D-06)

Visibility gate (client-side UX; the server re-checks — IDOR-safe): show the upload/remove controls when **the viewer is the character's assignee** (`RosterCharacter.is_mine === true`) **OR the viewer is an officer** (`session.isOfficer === true`). For a bank/bot toon (`is_bank_toon` / `is_guild_bot`, no assignee — D-06), only `isOfficer` unlocks the controls. Hidden entirely otherwise (no disabled ghost button — absent, matching how the app hides officer-only affordances). The controls sit **directly beneath the portrait frame**, inside the figure column, at `8px` (sm) below the frame.

Upload flow (D-03 — base64-in-JSON, no multipart):

| # | State | UI |
|---|-------|-----|
| 1 | Idle, no portrait | **Add photo** button (accent). Help text beneath: the formats/size hint. |
| 1' | Idle, portrait set | **Change photo** + **Remove photo** (destructive) side by side. |
| 2 | Picking | Native hidden `<input type="file" accept="image/png,image/jpeg,image/webp">` triggered by the button; label **Choose an image…**. `accept` excludes SVG/GIF (D-04 — SVG is an XSS vector, GIF/animated out of scope). |
| 3 | Client validation | On pick: reject non-PNG/JPEG/WebP (→ wrong-type error) and files whose **decoded** bytes would exceed the cap (→ too-large error). This is UX defense-in-depth; the **server re-sniffs magic bytes + re-enforces the ≤256 KB cap** and is authoritative. |
| 4 | Client downscale | Downscale/crop to a **square ~256–512px** (D-04, recommended) via canvas before base64-encoding, so the stored blob stays small. Discretion: client-side downscale is the default; server-side is allowed but the client path keeps the blob small pre-flight. |
| 5 | Preview + confirm | Show the downscaled image in the frame as a preview + **Save photo** / **Cancel**. Cancel restores the prior state (portrait or fallback) with no request sent. |
| 6 | Saving | **Uploading…** with the spinner; button disabled; controls locked. POST base64-in-JSON through the `postJSON` write core (the `charmeta.go` JSON-POST shape). |
| 7 | Success | Frame shows the new portrait (bump the local `portrait_updated_at` so the cache-bust `?v=` changes and the fresh blob loads); success message (`aria-live`). |
| 8 | Error | The frame reverts to its prior state; the matching error string renders (`aria-live`, `--status-missing`); no partial write. A mid-session 401 hands off to the site AuthGate (the `authGuard` context pattern); a 403 (`not_authorized`) also routes through it. |

Remove flow (D-08): **Remove photo** → confirm ("Remove photo:" copy) → `DELETE /api/v1/characters/{name}/portrait` via the credentialed write core → on success the frame reverts to the silhouette fallback + the remove-success message; same assignee-or-officer gate.

### Accessibility (WCAG — required)

- The file-picker trigger is a real `<button>` (or a `<label>` bound to the `<input>`) — **keyboard-operable**, `44px` min hit area, `:focus-visible { outline: 2px solid var(--accent); outline-offset: 1–2px }` (the app's focus idiom).
- Every control has an **accessible label** (the visible verb+noun label suffices; the hidden `<input type="file">` gets an `aria-label="Choose a portrait image"` or an associated `<label>`).
- Validation + success + error messages use `aria-live="polite"` and `--status-*` colors that already clear contrast per theme (mirrors `CharMetaForm .result`).
- The portrait `<img>` carries meaningful `alt={name}`; the decorative fallback silhouette stays `aria-hidden` (the name is already in the char-head `<h1>`).
- The frame's interactive/focus states respect `@media (prefers-reduced-motion: reduce)` (no scale/transition), consistent with `PaperdollSlot`.
