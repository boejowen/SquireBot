# Phase 30 — UI Design Contract

> Visual and interaction contract for the SquireBot web app's **5-tab navigation shell**.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **This is a CHROME/ROUTING rework of an existing SvelteKit app.** The visual language is
> ALREADY LOCKED — five EQ themes, `[data-theme]` single source of truth, established tokens
> and component idioms. This spec does NOT invent a palette; it pins the precise layout,
> interaction, states, accessibility, and responsive behavior of the navigation shell so the
> planner and executor have an unambiguous contract. Every token, size, and copy string below
> is either (a) lifted verbatim from the live codebase, or (b) the smallest extension of an
> existing idiom, noted as such. Design decisions D-01..D-08 (30-CONTEXT) and the winning
> sketch 001 / Variant A are encoded here, not re-litigated.

## Design System

| Property | Value |
|----------|-------|
| Tool | none (no shadcn — SvelteKit + Tailwind v4 + hand-rolled EQ-theme tokens) |
| Preset | not applicable |
| Component library | none (bespoke Svelte 5 runes components; `@lucide/svelte` icons only) |

| Theme system | `[data-theme="<key>"]` written once on `+layout.svelte`'s `.theme-root`; 5 keys: `velious` (default) · `vanilla` · `kunark` · `minimalist` · `heavy`. **All 5 must render the shell correctly — no re-skin (WEB out-of-scope: "existing 5 EQ themes reused unchanged").** |

**Locked constraint:** every new shell affordance reads colors/fonts ONLY through the theme
tokens below. No literal hex, no hardcoded font names, no per-component re-theming. A theme
swap is a single attribute write — the shell must inherit it for free.

## Spacing Scale

The codebase already uses a strict 4-based scale (verified in SiteShell, SettingsMenu,
+page.svelte). Reuse it exactly — do not introduce new spacing values.

| Token | Value | Usage in the shell |
|-------|-------|--------------------|
| xs | 4px | Tab-strip inter-tab gap; badge inset padding; identity-cluster gap |
| sm | 8px | Tab vertical padding; search-bar internal padding; menu-item gap |
| md | 16px | Header control gap; search bar → tab-body gap; tab horizontal padding |
| lg | 24px | Settings section vertical rhythm; `<main>` content gap; footer padding |
| xl | 32px | Header/main/footer horizontal gutters (desktop) |
| 2xl | 48px | Placeholder ("coming soon") vertical centering block |

**Touch-target exception (existing rule):** every interactive nav affordance (tab, identity
trigger, menu item, search input, badge-host link) has `min-height: 44px` (and `min-width:
44px` for icon-only buttons) REGARDLESS of visual padding. This is the established WCAG
touch-target floor and is non-negotiable. Horizontal gutters collapse to **16px** below 640px
(existing `@media (max-width: 640px)` rule in SiteShell — keep it).

Exceptions: none beyond the 44px touch floor noted above.

Roles are already declared across the live UI-SPEC lineage and rendered in
SiteShell/SettingsMenu/+page.svelte. Reuse verbatim — this shell adds NO new type roles.

| Role | Size | Weight | Line Height | Where in the shell |
|------|------|--------|-------------|--------------------|
| Body | 16px | 400 (`--font-body`) | 1.5 | Placeholder body copy, search input text, settings section prose, identity username at rest |

from the body's serif at-rest text.

**Numeric alignment:** any count (the unread badge) uses `font-variant-numeric: tabular-nums`
(existing `.unread-badge` rule).

## Color

The five themes each redefine the same token set; values below are the **Velious default**
(`:root` / `[data-theme="velious"]`) for illustration. The CONTRACT is the token NAME and its
ROLE, which holds across all five themes.

| Role | Token | Velious value | Usage |
|------|-------|---------------|-------|
| Dominant (~60%) | `--bg` | `#060b18` | Page background, `<main>` surface |
| Secondary (~30%) | `--panel` | `#0f1729` | Header gradient (`linear-gradient(var(--panel), var(--bg))`), tab strip backdrop, identity dropdown panel, Settings section cards, search-input fill |
| Accent (~10%) | `--accent` | `#a8c5e0` | **Reserved list below — never "all interactive elements"** |
| Destructive | `--destructive` (= `--status-missing`) | `#e88a8a` | Sign-out hover affordance ONLY if a destructive treatment is wanted; otherwise Sign out is a plain menu item. No other destructive action exists in this phase. |
| Border | `--border` (falls back to `--accent`) | — | Header bottom rule, tab-strip bottom rule, panel borders, search-input border at rest |
| Text | `--text` | `#d4dee8` | All at-rest copy |

**Accent reserved for (explicit, closed list):**
1. The **wordmark** ("SquireBot").
2. The **active tab**: its label color + its 2px `border-bottom` indicator (`border-bottom-color: var(--accent)`).
3. **Hover/focus state** of an inactive tab's label (transitions from `--text` @ 0.7 opacity → `--accent`).
4. The **unread badge fill** on the Wishlist tab (accent background, `--bg` text — the one inverted token use).
5. The **focus-visible outline** on every focusable shell affordance (`outline: 2px solid var(--accent)`).
6. Section **headings / eyebrows** inside Settings and Wishlist regions (existing `.coin-summary-title` / `.label` idiom — accent uppercase label).
7. The **identity-trigger** caret/label on hover/open (matches the old gear's `:hover { color: var(--accent) }`).

Accent is NOT used for: at-rest tab labels, body copy, placeholder prose, search-input text,
inactive borders beyond the standard `--border`, or any decorative fill. Inactive tabs sit at
`opacity: 0.7` in `--text` and only reach accent on hover/focus/active — this is what keeps the
active-tab signal legible against a strip of five.

**Heavy-theme caveat (carry forward):** Heavy inverts data rows (`--row-bg`/`--row-text`) but
the SHELL chrome (header, tab strip, identity, footer) stays on the dark frame — the tab strip
is chrome, not a data row, so it does NOT take the parchment treatment. Verify the accent
(`#f0d088`) active-tab underline reads against Heavy's `--panel` (`#1a0e05`); it does.

## Layout & Interaction Contract

> This is the load-bearing section for a chrome rework. The tables above are tokens; this is
> the structure the executor builds.

### A. Global frame (replaces the SiteShell header nav)

```
┌─────────────────────────────────────────────────────────────┐
│  SquireBot (wordmark, Display 28px, accent, → home)   Joe ▾  │  ← header row (panel→bg gradient, --border bottom)
├─────────────────────────────────────────────────────────────┤
│  CHARACTERS   INVENTORY   BANKS   WISHLIST ③   SETTINGS       │  ← tab strip (panel backdrop, --border bottom)
├─────────────────────────────────────────────────────────────┤
│  [ per-tab search bar — only on tabs with searchable content ]│  ← top of tab BODY, not the strip
│                                                               │
│  …tab body (route content)…                                   │
└─────────────────────────────────────────────────────────────┘
```

- **Wordmark** stays top-LEFT, unchanged (`<a href="/">`, Display 28px, accent, no underline,
  focus-visible 2px accent outline). Still links home.
- The header's old nav links (`Inventory` / `Wantlist` / `Notifications` + badge) and the
  **gear `SettingsMenu` are REMOVED** (D-06). What remains top-right is ONLY the identity +
  Sign-out affordance (section C). The invisible `[data-theme]` writer chain
  (`+layout → SiteShell`) stays — only the *picker location* moves into Settings.
- The **tab strip is a sibling band UNDER the header**, full-bleed to the same `xl`(32px) /
  16px-mobile gutters. It is the primary navigation and is present on **every** route
  (reachable from any page, D-01 / NAV-01) — i.e. it lives in the layout, not per-page.

### B. The tab strip (NAV-01)

**Order is fixed and spec-literal:** Characters · Inventory · Banks · Wishlist · Settings.
Tabs are **real route links** (`<a href>` to `/characters` `/inventory` `/banks` `/wishlist`
`/settings`), NOT buttons — D-01 makes each tab a deep-linkable SvelteKit route, so the active
state derives from `$page.url.pathname`, not client state. Using `<a>` (not `<button>`) gives
native middle-click/open-in-new-tab and correct browser history for free.

| State | Treatment (extends the live `.tab` / `.char-meta-nav` idiom) |
|-------|--------------------------------------------------------------|
| At rest (inactive) | `--text`, `opacity: 0.7`, `border-bottom: 2px solid transparent`, Label type (13px display uppercase, 0.08em) |
| Hover | `opacity: 1`, `color: var(--accent)` |
| Focus-visible | `outline: 2px solid var(--accent)`, `outline-offset: -2px` (inset, so it doesn't clip under the strip's bottom rule) |
| **Active** (current route) | `color: var(--accent)`, `border-bottom-color: var(--accent)`, `opacity: 1`, **`aria-current="page"`** |
| Min hit target | `min-height: 44px`, padding `8px 16px` |

The active-tab indicator is the **2px accent bottom border + accent label** — the EXACT
treatment already shipped for the in-page `.tab.active` in +page.svelte. One tab is active at
all times. The strip's own `border-bottom: 1px solid var(--border)` sits behind the active
tab's 2px accent border so the active tab "owns" that segment of the rule.

### B2. The unread badge on the Wishlist tab (NAV-04 / D-07)

The badge **moves off the header onto the Wishlist tab label** — this is the single visual
delta from the old `.notify-nav` badge, repointed.

- **Placement:** a small accent-fill pill immediately right of the word "WISHLIST" inside the
  same tab link (sketch 001 renders it inline: `Wishlist ③`). It is part of the tab's 44px hit
  target — the badge itself is not separately clickable.
- **Visual:** reuse `.unread-badge` verbatim — `min-width: 18px`, `padding: 0 4px`,
  `font-size: 13px`, `font-weight: 600`, `line-height: 18px`, `font-variant-numeric:
  tabular-nums`, `color: var(--bg)`, `background: var(--accent)`, `border-radius: 9px`. Inline
  (sketch) rather than absolutely-positioned top-right — the tab is wide enough to host it on
  the baseline; `margin-left: 6px` (xs-ish) before it.
- **Count source:** the existing `$unreadCount` store + `refreshUnread()` (server-truth,
  owner-scoped, re-fetched on mount + every route change — unchanged). No badge when count is 0
  (a "0" is noise — existing rule).
- **Cap:** `9+` past 9 (guild scale — the existing `count > 9 ? '9+'` rule, NOT "99+").
- **Accessibility (existing contract, preserved):** the COUNT is the non-color signal and MUST
  reach screen readers via the tab link's accessible name, e.g.
  `aria-label="Wishlist, 3 unread"` (mirrors the live `notifyLabel`). The pill span itself is
  `aria-hidden="true"` so the count isn't double-announced. When count is 0 the label is just
  "Wishlist" (no "0 unread"). The badge must never be the SOLE (color-only) signal.

### C. Identity + Sign out (top-right) — replaces the gear (D-06)

A minimal **"Joe ▾"-style** affordance (sketch 001 "What to Look For" — web convention; users
expect sign-out top-right). It REPLACES the `SettingsMenu` gear. Recommended shape (simplest
end-user experience): keep the existing dropdown MECHANICS, swap the trigger glyph and prune
the menu to identity-only items.

- **Trigger:** a `<button>` showing the avatar (Discord CDN PNG via the existing `avatarUrlFor`
  helper, or the `User` glyph fallback) + the username + a `ChevronDown` (▾) caret. Officer
  shield badge stays if `session.isOfficer`. `min-height: 44px`. `aria-haspopup="menu"`,
  `aria-expanded` bound to open, `aria-controls` the panel id, `aria-label` includes the
  username (e.g. "Account menu, Joe"). The username renders via plain `{}` interpolation ONLY
  (Svelte auto-escape — the live T-15-22 XSS rule; never raw-HTML, the alt text is the same
  escaped username).
- **Menu contents (pruned):** ONLY (1) the identity header (avatar / officer shield / username,
  already in the panel), and (2) **Sign out** (reuses the live `signOut()` + `signingOut`
  guard + `LogOut` glyph). Everything else the old gear held — Theme, Watcher codes, Set class
  & level, My characters, Admin — **moves into the Settings tab (D-05/D-06)** and is GONE from
  this menu. A "Settings" item here is OPTIONAL and redundant with the Settings tab; per
  "one place per concept," do NOT duplicate it — the tab strip is the canonical route in.
- **A11y (unchanged from SettingsMenu):** `role="menu"` panel, `role="menuitem"` items, Escape
  closes + restores focus to the trigger, outside-pointerdown closes, route-change closes, focus
  moves to the first item on open. `focus-visible: 2px solid var(--accent)`.
- **Why a dropdown and not just a "Sign out" button:** the dropdown already exists, already
  carries identity, and a 2-item menu (identity + sign out) is the lowest-churn path that
  matches the "Joe ▾" sketch convention. Reuse > rebuild.

### D. Per-tab scoped search (NAV-02 / D-08) — NO dead search bars

The search bar lives at the **top of the tab BODY** (under the strip), full content width,
consistent placement across tabs (Variant A pattern). It is shown **only where searchable
content exists this phase**:

| Tab | Phase-30 search | Treatment |
|-----|-----------------|-----------|
| **Wishlist** | YES — whatever the current wantlist surface offers (rehomed). | Functional scoped search over the wantlist (the existing WantlistPanel filter/add idiom; full WISH-07 cross-wishlist search is Phase 34, not now). |
| **Settings** | YES — a **settings search** that filters/jumps to sections (section D2). | Functional. |
| **Characters** | **NO bar** — friendly "coming soon" placeholder (section E). | An inert box is the worse experience (D-08) — omit it entirely. |
| **Inventory** | **NO bar** — placeholder. The home cross-character `SearchBox` becomes THIS tab's search in Phase 32. | Omit. |
| **Banks** | **NO bar** — placeholder. | Omit. |

**Search-input visual (when present), from the sketch + live tokens:** full-width,
`background: var(--panel)` (or the `--slot`-equivalent fill), `border: 1px solid var(--border)`,
`color: var(--text)`, Body 16px, `padding: 8px 12px` (sm/md), `border-radius: 4px`, placeholder
in dimmed `--text`. Focus: `border-color: var(--accent)` + `outline: 2px solid var(--accent)`
(focus-visible). `min-height: 44px`. A one-line **search-hint** below in dimmed Body 13–14px
when guidance helps (e.g. "Your characters match first" once Characters ships — not this phase).

### E. Placeholder tab body (Characters / Inventory / Banks) — never strand the user (D-03 / D-03b)

Each stub tab renders a **friendly "coming soon" placeholder** centered in a dashed-border
card (the sketch `.placeholder` idiom: `border: 1px dashed var(--border)`, `border-radius:
4px`, `padding: 48px 24px` (2xl/lg), `text-align: center`, dimmed `--text`). Structure:

1. A **Heading** (20px display): the tab name. (e.g. "Characters")
2. A one-line plain-language **description of the question this tab will answer** (Body 16px,
   dimmed) — e.g. Characters: "What does this character have? — the in-game-style inventory
   window lands here soon." (Copy table below has the exact strings.)
3. **A real, working link to the preserved classic view (D-03b — load-bearing).** The
   Characters/Inventory/Banks placeholders MUST each carry a visible, labeled link that keeps
   the existing consolidated inventory/gear/spell/bank views reachable, so no guildie loses
   "what's in the guild?" mid-transition. Treatment: an accent-bordered link styled like the
   live `.record-coin` affordance (`min-height: 44px`, display uppercase 13px, `border: 1px
   solid var(--border)`, accent text, hover `color-mix(accent 12%)`). The exact destination
   (an interim `/legacy`-style path vs. embedded body vs. deep link) is **planner's discretion
   per D-03b** — the CONTRACT is only that the link is present, labeled, and works.

**Default landing (D-04):** during the stub window, `/` resolves to the **preserved functional
inventory surface**, NOT the Characters "coming soon" stub (greeting an active user with an
empty placeholder is the worse experience). The placeholder text on Characters/Inventory/Banks
must read as "building this," never as a dead end.

### F. Settings tab (NAV-03 / D-05) — ONE page, in-page sections

Settings is a SINGLE route (`/settings`) composing the EXISTING panels as stacked in-page
**sections** (NOT a menu of links to sub-pages — that adds navigation round-trips). Sections,
in order:

1. **Theme** — the `ThemePicker` component, REHOMED here (D-06). Same `bind:theme` chain — the
   picker mutates the `$bindable` theme; `+layout`'s `$effect(applyTheme)` stays the single
   `[data-theme]` writer. Only the picker's *location* moves.
2. **Watcher Codes** — `WatcherCodesPanel` (was `/account`).
3. **Set Class & Level** — `CharMetaForm` (was `/char-meta`).
4. **My Characters** — `MyCharactersPanel` (was `/my-characters`).
5. **Admin** — `AssignmentAdminPanel` + `MonitorAdminPanel`, **officer-only** (`{#if
   session.isOfficer}`; the server re-checks every `/admin` endpoint — the hidden section is
   UX suppression, never the gate). Non-officers never see this section or its search hits.

**Section layout:** each section is a `--panel` card (`border: 1px solid var(--border)`,
`border-radius: 6px`, `padding: 24px` (lg)), titled with an accent display Heading (20px) +
optional dimmed Body purpose line — the established `.form-card` / `.form-title` /
`.form-purpose` rhythm (24px gap between sections, lg). Each section carries a stable `id`
(e.g. `id="settings-theme"`) so the search can jump to it and so old deep links can land
(`/account` → `/settings#settings-watcher-codes`, D-02).

**F2. Settings search behavior — RECOMMENDATION: live in-page filter, NOT jump-to-section.**
A search input at the top of the Settings body filters which SECTIONS are visible as you type
(matching on section title + a small keyword set per section, e.g. "theme", "password"-no,
"watcher"/"code"/"PC", "class"/"level", "characters", "admin"/"officer"/"monitor"). Rationale
(simplest end-user experience, the phase's governing rule): a guildie types "watcher" and sees
exactly the Watcher Codes section, no scroll-hunt, no extra click, no navigation. Empty query =
all sections shown (the default). A jump-to-section dropdown was rejected because it adds a
selection step and leaves the user to scroll. When the filter matches nothing, show a compact
"No settings match '{query}'" line (Body, dimmed) — do not blank the page. The search input
reuses the section-D search-input visual + 44px target + accent focus.

### G. Wishlist tab (NAV-04 / D-07) — rehomed wantlist + notifications, at the layout level

`/wishlist` composes, top-to-bottom (all EXISTING components, rehomed — Phase 30 does NOT do
the per-slot rework, that's Phase 34):

1. **The wantlist surface** — `WantlistPanel` (today's `/wantlist` content: intro + add form
   in a 720px card, filter bar + grids full-width — the existing layout, unchanged).
2. **Notifications region** — the `/notifications` content rehomed: `NotificationPrefsPanel`
   (global opt-in/cooldown prefs) + a divider + `NotificationInbox` (the alert inbox). Per-item
   ping toggles already live on wantlist rows (the existing mute bell) and stay there.
3. **The unread badge** on the Wishlist TAB label (section B2) is the at-a-glance signal that
   the inbox below has unread alerts.

**Composition note for the planner:** the wantlist and the notifications region are two
distinct concerns stacked on one route. Keep the existing `.form-card` (720px) rhythm for the
forms and let grids break to content width (the live wantlist/home pattern). A clear divider
or section heading ("Notifications") separates the inbox/prefs from the wantlist above it so
the rehome reads as deliberate, not bolted-on. One mental model: every alert is a wishlist-item
ping, so the inbox belongs with the wishlist (D-07).

### H. Responsive / mobile collapse of the 5-tab strip — RECOMMENDATION: horizontal scroll

The existing header already `flex-wrap`s, but for a 5-tab PRIMARY nav, wrapping to two rows is
visually muddy and breaks the "strip" read. **Recommendation (simplest, no hidden affordances):
a single-row horizontally-scrollable strip below ~520px**, not a wrap and not a hamburger menu.

- **Mechanism:** the tab strip is `display: flex; flex-wrap: nowrap; overflow-x: auto;` with
  `-webkit-overflow-scrolling: touch` and `scrollbar-width: thin` (or hidden chrome with a
  subtle edge fade). All five tabs stay on one line; the user swipes. `scroll-snap-type: x
  proximity` with `scroll-snap-align: start` on each tab makes it feel intentional.
- **On load / route change**, scroll the ACTIVE tab into view (`scrollIntoView({ inline:
  'nearest', block: 'nearest' })`) so you always see where you are. This is the key
  anti-confusion rule — never leave the active tab scrolled off-screen.
- **Why not a hamburger:** five short labels fit a horizontal scroll comfortably; a menu hides
  the primary nav behind a click and a 5-item menu is more taps than a swipe (a worse
  end-user experience for the app's main navigation). Why not wrap: two ragged rows make the
  active-indicator border ambiguous and waste vertical space above dense grids.
- **Gutters** collapse to 16px below 640px (existing rule). The identity "Joe ▾" trigger may
  drop the username text and show avatar + caret only below ~400px to preserve the header row.

### I. Empty / error / loading states (reuse StateBlock)

This phase ships no NEW data fetch of its own, but the rehomed surfaces carry their existing
states. Reuse `StateBlock` verbatim — do NOT invent new copy:

- Wishlist with zero wants → `kind="no-wants"` ("Your wantlist is empty…").
- Notification inbox with zero alerts → `kind="no-notifications"` ("No alerts yet…").
- Settings sub-panels keep their own empty states (`no-codes`, `no-bank-toons`,
  `no-promotable-users`) — unchanged.
- A fetch failure on any rehomed surface → `kind="error"` ("Couldn't load the data…" + Retry).
- The shell itself (header, tab strip, identity) is static chrome — it has no loading state; it
  renders immediately around whatever the tab body resolves to.

## Accessibility Contract (NAV-01..04)

A11y is load-bearing for a navigation rework — these are hard requirements, not nice-to-haves.

1. **Active tab:** the current-route tab carries `aria-current="page"` (the active visual state
   alone is NOT sufficient). Exactly one tab is current at all times.
2. **Tabs as links:** the strip is `<a href>` route links, not a `role="tablist"`/ARIA tabs
   widget — they navigate pages, so native link semantics + `aria-current` are correct and
   simpler than a roving-tabindex tab widget. **Keyboard nav = native Tab/Shift-Tab through the
   links + Enter to follow** (no custom arrow-key roving needed because each is a real link to a
   real route). Every tab is reachable by keyboard and shows a visible focus ring.
3. **Focus-visible:** every focusable shell affordance (tab, identity trigger + menu items,
   search input, placeholder link, wordmark) shows `outline: 2px solid var(--accent)` on
   `:focus-visible` (tabs use `outline-offset: -2px` to avoid clipping under the strip rule;
   others use `+2px`). This is the universal, already-shipped focus treatment.
4. **44px touch targets:** every interactive affordance has `min-height: 44px` (icon-only
   identity trigger also `min-width: 44px`).
5. **Unread badge announced:** the count reaches screen readers via the Wishlist tab link's
   `aria-label` ("Wishlist, {N} unread"); the pill is `aria-hidden`. Color is never the sole
   signal. No badge / no "unread" text when count is 0.
6. **Identity menu a11y (existing SettingsMenu contract, preserved):** `aria-haspopup="menu"`,
   `aria-expanded`, `aria-controls`; `role="menu"` panel with `role="menuitem"` items; Escape
   closes + restores focus to the trigger; outside-click + route-change close; focus moves into
   the menu on open.
7. **Settings sections:** each section is a landmark/region with a heading and a stable `id`
   (so old deep links land and so the search can target it). The settings-search input has an
   accessible label ("Search settings").
8. **Reduced motion:** any tab-scroll-into-view, hover transition, or theme transition honors
   the global `@media (prefers-reduced-motion: reduce)` rule in app.css (transitions become
   instant). The mobile `scrollIntoView` should pass `behavior: 'auto'` (no smooth scroll) when
   reduced-motion is set.
9. **Theme-independence:** all 7 a11y treatments above must hold under all 5 themes — verify the
   accent focus ring + active-tab underline have sufficient contrast in `minimalist` (low-chroma
   accent `#b8915c`) and `heavy` (`#f0d088` on near-black panel). Both pass; spot-check at build.
