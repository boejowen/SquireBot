## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| EC job → PigParse (third-party HTTP) | untrusted getdetails JSON + the item segment in the outbound URL |
| third-party auction data → DM embed | price/seller/timestamp from PigParse rendered into a DM the bot sends a guildie |
| EC job → Discord (via notify) | the embed DM send (gated by the spine) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-21-08 | Tampering (SSRF / path traversal) | ec/urls.go getdetails URL build | mitigate | Hardcoded host/scheme constant; the id/name segment escaped via enrich.EncodeURIComponent; ids/names come from the catalog/wantlist, never a request body. An item name with special chars cannot break the URL or traverse. |
| T-21-09 | DoS / trust (DM carpet-bomb → users mute → permanent 50007) | the cursor/diff + send loop | mitigate | Cursor diff (t>cursor) + first-sight baselining (no history replay) + advance-only-on-success + the inherited RecentAlertExists cooldownEC=22h dedup. A standing auction is never re-DMed; a restart replays nothing (ROADMAP criterion 4). |
| T-21-10 | Elevation (ungated/duplicated send) | ec.RunMatch send path | mitigate | EVERY send routes through notify.Send (both gates + dedup + alert_log); the job never calls ChannelMessageSendEmbed directly (acceptance-grep enforced). The mute gate is upstream in wantmatch.ForItem (muted=0). |
| T-21-11 | Info disclosure (PII) | EC slog + the players map | mitigate | V7 — log source/item_id/want/status only; never the DM body, embed content, raw item names beyond ids, or the players map. |
| T-21-12 | DoS (malformed/oversized PigParse body) | ParseItemDetail + politefetch | mitigate | ParseItemDetail is malformed-tolerant (Plan 01, no panic on null `p`/missing fields); politefetch caps the body at ~16 MB; a per-item parse failure is logged and skipped (loop survives, D-07). |
| T-21-13 | Spoofing (wrong DM recipient) | DiscordUserID source | accept | DiscordUserID comes from wantmatch.Hit (resolved from the want row), never a request body — no new auth surface, no IDOR (no new HTTP route). |
</threat_model>
