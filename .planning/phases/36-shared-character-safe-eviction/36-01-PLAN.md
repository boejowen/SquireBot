<objective>
Narrow the per-owner eviction cascade so evicting a guildie removes ONLY that member's OWN characters — never a SHARED character that another guildie also plays and uploads (OWN-03) — AND make the eviction-preview contract carry enough signal that an all-shared owner (every live char shared) stays evictable through the web UI (the plan-checker BLOCKER). Today `EvictOwnerTx(X)` runs `UPDATE character SET is_removed=1, grace_until=? WHERE owner_id=X AND is_removed=0`, which sweeps EVERY live char stewarded by X — including a shared char like the Kim/Aenriel-class shared-login case that a second guildie still actively uploads. After this plan a char is preserved when at least one OTHER guildie has uploaded it.

"Shared" is derived from the EXISTING `audit_log` `cross_owner_write` trail (D-01) — NO new table, NO migration. Every cross-owner upload since `260621-u6j` appends a `cross_owner_write` row `(event, char_name, attempting_owner_id, current_owner_id)` (binding.go `auditCrossOwnerWrite`). A char stewarded by the evicted owner X is **shared** iff there EXISTS a `cross_owner_write` row with `char_name = <char>.name (COLLATE NOCASE) AND attempting_owner_id <> X`. Phase 36 is the FIRST reader of `cross_owner_write` (today there are none).

The narrowed predicate lives in ONE reusable SQL fragment (`sharedCharPredicate`) shared by the cascade (`EvictOwnerTx`), the preview list (`PreviewEviction`), AND the preserved-shared count (`CountPreservedShared`) — the explicit Phase-35 CR-01 lesson (the picker read and the write path diverged → BLOCKER). The repoint's "most-recent other sharer" subselect is captured in a SECOND named const (`recentOtherSharerSubquery`) reused by BOTH the repoint's SET clause and its IS-NOT-NULL guard, so those two copies can never drift in event-string / COLLATE (the plan-checker WARNING fix). The guild-code revoke is UNCHANGED — evicting an owner who only stewards shared chars returns removedCount 0 but still revokes their code so their watcher stops uploading.

**Preview-contract change (the BLOCKER fix, backend half):** the eviction-preview reply gains an additive snake_case field `preserved_shared_count int` — the count of the owner's live chars that survive *because they are shared* (the inverse complement of the narrowed remove-set, computed by `CountPreservedShared` off the SAME `sharedCharPredicate`). With both `characters` (the narrowed remove-set) and `preserved_shared_count` on the reply, the preview is never empty for an owner who still has live characters: an all-shared owner sends `characters:[]` but `preserved_shared_count > 0`, which the web plan (36-02) uses to keep the Evict button enabled (code-only revoke). Banks/bots are already eviction-safe via Phase 35's sentinel (`ErrCannotEvictSentinel` guard stays first); this plan does NOT re-litigate bank survival.

Purpose: an evicted member loses only their OWN data; shared characters other guildies still play stay live; an all-shared owner remains revocable.
Output: a narrowed `EvictOwnerTx` cascade + a parity-locked `PreviewEviction` + a `CountPreservedShared` count + a WARNING-fixed surviving-shared repoint + the additive `preserved_shared_count` preview field + full TDD proofs — in `store/eviction.go`, `store/eviction_test.go`, and `webadmin/eviction.go`. NO schema migration (schema stays v15, D-05). Backend only in this plan (the web change is 36-02, wave 2); watcher UNTOUCHED; NO `v*` tag.

This is the backend half of the (now backend + web) Phase 36 (3 tasks). The web change genuinely DEPENDS on the new `preserved_shared_count` preview contract this plan ships, so it is a separate wave-2 plan (36-02). All backend sources (GOAL/REQ OWN-03/CONTEXT D-01..D-06) converge on the same seam (`EvictOwnerTx` + `PreviewEviction` + the preview handler); nothing exceeds the context budget.
